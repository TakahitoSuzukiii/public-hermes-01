今週は「セキュリティ運用（SOC = Security Operation Center、セキュリティ監視・対応の専門チーム）のアラート初動対応をClaude Codeで自動化した2社の実践事例」「New RelicのSLO（Service Level Objective、サービス品質の目標値）違反調査をClaude Codeの『スキル』として型化した事例」「PowerPoint自動生成の3手法比較」「Terraformを使ったAWSインフラのIaC（Infrastructure as Code）化と権限分離の実践」の4カテゴリで整理しました。前週（9/7号）はExcel集計自動化とセキュリティ診断の2層防御が中心でしたが、今週は「アラートが鳴ってから人が動き出すまでの初動」をAIに任せる、より実務直結型の事例に重点を移しています。いずれも「サーバーを新設せず、既存のSlack・ノートPCの認証環境をそのまま流用する」という小さく始める設計思想が共通していた点が印象的でした。

## 1. ITインフラ/サーバ運用保守のルーティンワーク自動化（PPT資料作成）

### Claude Codeでパワポを自動生成する実務ガイド｜提案書・月次レポート・営業資料を爆速化する
- 出典: https://aurant-technologies.com/blog/claude-code-powerpoint-jidoka/
- 内容: PowerPoint自動生成の3つのアプローチ（①Anthropic公式のpptxスキル、②python-pptx（既存の.pptxテンプレートを読み込んでデータ差し替えができるPythonライブラリ）、③Claude for PowerPoint＝Microsoft 365アドイン）を、難易度と用途別に比較した実務ガイドです。会社の月次報告資料などで最も採用実績が多いのは②のpython-pptx方式で、既存テンプレートのデザインを壊さずデータだけ差し替えられる点が評価されています。
- 便利さ: 「まず何から試せばよいか」という導入初期の疑問に、3手法の使い分け基準という具体的な判断軸を与えてくれます。社内テンプレートを崩さず自動更新したい担当者にとって、遠回りせず本命の手法（python-pptx）にたどり着ける実務的なガイドです。
- 注意点: python-pptx方式は既存テンプレートの構造（プレースホルダーの位置など）に依存するため、テンプレート側の変更頻度が高い組織では都度メンテナンスコストが発生します。

## 2. ゼロデイ攻撃対策・セキュリティ運用の自動化

### Claude CodeがSOC業務を全自動でやってくれるってさ
- 出典: https://techblog.zozo.com/entry/soc-claude-agent
- 内容: ZOZOの情報セキュリティ部が、SOC（Security Operation Center）の3人体制で日々処理しきれない大量のセキュリティアラートに対し、Claude CodeによるSOC Agent（自動アラートトリアージ〈優先順位付け〉エージェント）を構築した事例。Splunk MCP（ログ検索基盤への接続規格）とOpenCTI MCP（脅威インテリジェンス基盤への接続規格）を組み合わせ、アラートの優先度評価と対応案の検討までを自動化し、結果をSlackに投稿する設計です。即時対応（実際の遮断操作など）は別のSOARツールに委ね、SOC AgentはRead権限のみで完結させている点が特徴です。
- 便利さ: 「AIに読み取り専用の権限だけ与えて初動の切り分けを任せる」という設計は、セキュリティ領域でAI活用を検討する際のリスクを抑えた導入モデルとして参考になります。SOCメンバーの負荷軽減だけでなく、対応の質を平準化（担当者による判断のばらつきを減らす）できる点も実務的な効果です。
- 注意点: Splunk MCP Serverの利用にはIP許可リストの設定など事前準備が必要で、SOCの業務知識（何を優先度高と判断するか）をどう的確にエージェントへ落とし込むかの設計コストは依然として残ります。

### Claude Code + MCP でアラート対応を自動化した話
- 出典: https://tech.asoview.co.jp/entry/2026/08/31/124801
- 内容: アソビューが、レジャー施設向けSaaS「ウラカタチケット」のエラーアラート一次分析を、専用サーバーを立てずにエンジニアの手元のClaude Code環境（Datadog MCP・GitHub MCP経由）で自動化した事例「pp_sentinel」。Slackのアラートスレッドへ原因・影響範囲・対応方針の分析結果を自動返信し、共有状態やheartbeatもSlackのピン留めメッセージとリアクションで代用する、インフラをほぼ持たない設計が特徴です。
- 便利さ: 「効果が未確認の段階で専用インフラを作るのは大げさ」という考えから、既存のノートPCと認証環境をそのまま流用する発想は、小規模チームがAI自動化を試す際の低コストな第一歩として非常に参考になります。深夜・休日など人手が薄い時間帯の一次判断を代替してくれる実用性も高いです。
- 注意点: 「誰かのPCが起動していないと処理が止まる」設計のため、24時間監視が必須の重大アラートには不向きで、あくまで「止まってもよい規模・重要度」のアラートに限定した使い方が前提になっている点に留意が必要です。

## 3. インフラ/クラウドエンジニア・SRE・CI/CD・Playwrightによる自動化

### Claude CodeのスキルでSLO対応を自動化したらめちゃくちゃ楽になった
- 出典: https://tech.uzabase.com/entry/2026/06/26/100727
- 内容: ユーザベース（NewsPicks Platform Engineeringチーム）が、New Relic（APM＝Application Performance Monitoring、アプリケーションの性能監視ツール）のSLO違反調査という「1回1.5〜4人時かかる泥臭い作業」を、Claude Codeの「スキル」（定型作業手順をあらかじめ定義しておく仕組み）として型化した事例。SlackのアラートURLを渡すだけで、エンドポイント特定・原因究明・改善案提示までの調査フローを自動で再現させています。
- 便利さ: 週次モニタリング会議で人が1件ずつ調べていた作業を型化することで、会議の時間を大幅に圧縮できた実例です。「まず単純なN+1問題（1回の親リクエストに対しN回の子アクセスが発生する非効率なパターン）から試す」という段階的な導入の進め方も、これからスキル化に取り組むチームにとって参考になる手順です。
- 注意点: スキルとして再現性を持たせるには、調査ログの型（エンドポイント・発生時刻・所要時間など）を事前に定義しておく必要があり、既存の調査フローが属人化・非定型なチームではまず手順の言語化から着手する必要があります。

## 4. ベストプラクティス、実際に構築・検証して効果があった手順書/実績

### Claude Codeではじめる、インフラ構築/運用 ── IaC編
- 出典: https://zenn.dev/nocall/articles/09534c8b6832a2
- 内容: 音声AI SaaS「nocall」を運営する企業が、AWSインフラをClaude CodeとともにTerraform（インフラ構成をコードで管理するツール）化した実践記。5日間で220ファイル・約1万行を追加し、検証環境ではClaude Codeに`terraform apply`（実際の変更適用）まで任せる一方、本番環境は`plan`（差分確認のみ）に権限を制限し、適用は必ず人が実行するという線引きを行っています。
- 便利さ: 「AIエージェントに本番DBを誤って削除された」という他社の実例を踏まえ、環境分離とTerraform管理によって「AIにどこまで任せるか」をアカウント単位で明確に線引きした設計は、AGENTS.mdのHITL（Human-in-the-Loop、人間が承認に介在する運用原則）とも通じる考え方で、そのまま参考にできます。
- 注意点: この効果は前提としてTerraformの網羅的な導入（既存の手動作成リソースの巻き取り）が必要で、IaC化が進んでいない組織では、まず既存構成の棚卸しという地道な準備工程が先に必要になります。

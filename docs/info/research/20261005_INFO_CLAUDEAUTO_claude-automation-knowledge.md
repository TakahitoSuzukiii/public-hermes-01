## 今週のテーマ

今週は「PowerPoint資料作成はAIに丸投げでは失敗する、指示の具体性が品質を決める」という基本に立ち返る記事と、「Notion・Google連携で週次レポートの収集〜作成〜保存を一気通貫自動化した」実践記、Anthropicが2026年4月に発表したセキュリティ特化モデル「Claude Mythos Preview」と防御的サイバーセキュリティ構想「Project Glasswing」の数千件規模のゼロデイ脆弱性（公開前の未知の脆弱性）発見の全体像、Playwright（ブラウザ自動操作ツール）を使ったE2Eテスト（エンドツーエンド＝実際の画面操作を模したテスト）の完全自動化事例2本、そして「Claude Code Routines（スケジュール実行機能）を実際に3日間運用してわかった料金・事故・止め方」という現場の生々しい記録を中心にまとめました。前週（9/28号）は「デザイン判断をAIから取り上げる設計思想」や「開発初期のセキュリティ全量スキャン実測」を深掘りしましたが、今週はそれと対になる形で「Anthropic自身が主導する国家規模のセキュリティ構想」と「個人が実際に自動実行機能を使って痛い目を見た記録」という、スケールの両極を併せて紹介します。

## 1. ITインフラ/サーバ運用保守のルーティンワーク自動化（PPT資料・Excelレポート作成）

### Claude CodeでPowerPoint資料は作成すべき？ 高品質な資料を作るための指示の出し方
- 出典: https://generative-ai.sejuku.net/blog/311199/
- 内容: Claude Codeはpython-pptx（PowerPointファイルをPythonから操作するライブラリ）やMCP（Model Context Protocol、AIが外部ツールを呼び出すための標準規格）経由でPowerPointファイルを生成できますが、スライド構成やデザイン要件を具体的に指示しないと「それなりの見た目」で終わってしまう、という実務目線の整理記事です。
- 便利さ: 「資料は作成すべきかどうか」という導入検討段階の判断基準から解説しており、これから試す人が過度な期待を持たずに始められる構成になっています。前週号で紹介した「デザインルールをコードにハードコードする」という解決策と合わせて読むと、同じ課題（AIにデザインを丸投げすると崩れる）への異なる対処レベル（指示を磨くか、ルールをコード化するか）を比較できます。
- 注意点: 記事自体は入門的な整理が中心で、具体的なプロンプト例や生成コードの公開は限定的です。実運用には前週号で紹介したような、自社フォーマットをコード側に固定する工程が別途必要になります。

### ClaudeとNotion・Google連携で週次レポートの収集〜作成〜保存を一気通貫で自動化
- 出典: https://note.com/hungrytiger/n/n7a9712993c77
- 内容: ClaudeとNotion（ノート・データベース型の情報管理ツール）、Google（Googleドキュメント・スプレッドシート等）の連携を組み合わせ、週次レポートに必要な情報収集からレポート作成、保存までを一気通貫で自動化した実践記です。
- 便利さ: 情報収集→作成→保存という3工程を別々のツールに任せず、連携設計で繋ぎきった点が実務的です。定例会議の削減効果にも触れられており、単発の資料作成ではなく「レポート運用全体」を自動化対象にする視点が参考になります。
- 注意点: Notion・Googleという特定ツール組み合わせへの依存が前提のため、社内の情報管理基盤が異なる場合はそのまま移植できず、連携部分の再設計が必要です。

## 2. ゼロデイ攻撃対策・セキュリティ運用の自動化

### Claude Mythos PreviewとProject Glasswing — AIが数千件のゼロデイ脆弱性を自律発見する防御的セキュリティ構想
- 出典: https://zenn.dev/galirage/articles/claude-mythos-preview （参考: https://gigazine.net/news/20260408-anthropic-claude-mythos-project-glasswing/）
- 内容: Anthropicが2026年4月、サイバーセキュリティ特化のプレビューモデル「Claude Mythos Preview」と、防御目的に限定してアクセスを提供する「Project Glasswing」を発表した件の解説です。Mythos PreviewはWindows・macOS・Linuxの全主要OS、主要ウェブブラウザにおいて数千件規模のゼロデイ脆弱性（公開前の未知の脆弱性）を発見したとされ、AWS・Apple・Microsoft等の有志企業連合に限定提供される形で運用されています。Anthropicは一般公開を見送り、「危険な出力を確実に止める安全策」を先に整えるとしています。
- 便利さ: 「AIによる脆弱性発見」が個社の内製スキャン（前週号で紹介したGMOグループの事例など）の延長線ではなく、Anthropic自身が主導する国家・業界横断規模の防御的インフラとして動き始めている、という全体像を掴めます。SWE-Bench Pro等のベンチマーク数値も示され、能力の高さと公開リスクのトレードオフが整理されています。
- 注意点: Mythos Previewは一般提供されておらず、今すぐ自社で同等の仕組みを再現することはできません。日本企業は2026年4月時点でProject Glasswingの有志企業連合に参加していないとの指摘もあり、国内での追随動向は別途ウォッチが必要です。

### 日本企業はProject Glasswingの枠外 ── CI/CDとAI開発エージェントで脆弱性修正を自動化する代替路線
- 出典: https://hatenabase.jp/blog/claude-mythos-japan-company-3-choices/
- 内容: 前述のProject Glasswingに日本企業が参加していない現状を踏まえ、国内企業が取れる代替策として「CI/CDパイプライン（GitHub Actions・GitLab CI等）の全社整備」と「Claude CodeやCursorなどのAI開発エージェントで脆弱性修正コードのドラフトを自動生成する」という2段構えのアプローチを提言した記事です。
- 便利さ: 「Anthropicの最先端モデルが使えないなら何もできない」ではなく、既存のCI/CD基盤とAIコーディングエージェントの組み合わせで防御力を上げるという、手の届く範囲の代替策を示している点が実務的です。前週号のGMOグループの「自動コミット禁止・人間レビュー必須」という運用とも方向性が一致します。
- 注意点: あくまで代替策としての提言であり、Mythos Previewのような大規模自律探索と同等の検出力を保証するものではありません。導入にはCI/CDの網羅的整備という前提作業が必要です。

## 3. インフラ/クラウドエンジニア・SRE・CI/CD・Playwrightによる自動化

### Claude Codeで実現するテスト計画から報告書まで完全自動化 ── Playwright E2Eテストの実践例
- 出典: https://qiita.com/Mor1yarty/items/5440ff56f2bc6649279a
- 内容: POSアプリケーション開発の続編として、テスト計画書の作成からPlaywrightによるE2Eテスト（エンドツーエンド＝実際の画面操作を模したテスト）実行、報告書生成までをClaude Codeで完全自動化した実践例です。
- 便利さ: 「テストコードだけ」ではなく「計画書→実行→報告書」という一連の工程をまるごと自動化対象にしている点が、前週号で紹介したクラスメソッドの対話型テスト構築（確認作業とテスト作成を分断しない手法）とは異なるアプローチとして参考になります。工程全体を通した自動化の設計がそのまま模写できる構成です。
- 注意点: POSアプリという比較的構造が単純な対象での実践例のため、複雑な業務システムでは計画書・報告書のテンプレート自体を自社向けに調整する手間が発生します。

### Claude Code × Playwright MCPで画面テストをほぼコード書かずに自動化
- 出典: https://blog.future.ad.jp/claude-code-playwright-mcp-test-auto
- 内容: Todoアプリを対象に、Claude CodeとPlaywright MCP（AIがブラウザを直接操作できるようにする仕組み）を使い、仕様書の作成からバグ検出までテストコードをほぼ書かずに自動化した事例記事です。
- 便利さ: 「手で全部確認するのがつらい」という小規模開発現場でも導入しやすい粒度の事例で、仕様書作成からバグ検出までの一連の流れが具体的に示されています。前述のMor1yarty氏の記事（計画書〜報告書の完全自動化）と組み合わせると、小規模〜中規模まで段階的に参考にできる構成です。
- 注意点: Todoアプリという小規模対象での検証であり、既存の大規模テストスイートへの統合や、CI上での安定した繰り返し実行についての知見は限定的です。

## 4. ベストプラクティス、実際に構築・検証して効果があった手順書/実績

### 【実録】Claude Code Routinesを3日間運用してみた ── 料金・事故・止め方の記録
- 出典: https://qiita.com/nogataka/items/3ff7b14684306ef413e0
- 内容: Claude CodeのRoutines（スケジュール実行機能）を実際に3日間運用し、発生した料金・事故・止め方までを生々しく記録した実践記です。Issueトリアージ（課題の優先度振り分け）の発火を「1時間3件まで」に制限するフックスクリプトなど、暴走を防ぐための実コードも公開されています。
- 便利さ: 「便利だった」で終わらず、実際に起きたトラブルとその対処法まで公開している点が非常に貴重です。AGENTS.mdのHITL（Human-in-the-Loop）原則が重視する「自動実行の上限・止め方を事前に決めておく」という考え方の、生きた実例として参考になります。
- 注意点: 3日間という短期間の記録であり、長期運用での費用傾向や事故パターンの網羅性には限界があります。導入前に自社の利用規模に応じた上限設計を別途検討する必要があります。

### Claude Codeの「loop」コマンドで繰り返し作業を自動化
- 出典: https://kiralab.jp/claude-code-loop-command-automation/
- 内容: Claude Codeの`/loop`コマンドを使い、デプロイの監視やビルドの完了確認といった「数分おきに同じ確認をする」繰り返し作業をAIに任せる方法を紹介した記事です。
- 便利さ: 複雑な技術を一度シンプルな指示に変換すれば、あとはAIが同じ確認作業を何度も繰り返してくれるという設計思想が分かりやすく説明されています。前述のRoutines運用記事（3日間の実録）と合わせて読むことで、「数分単位の繰り返し」はloop、「曜日・時刻指定の定期実行」はRoutinesという使い分けの判断材料になります。
- 注意点: loopコマンドも無制限に動かすと想定外の繰り返し実行につながるリスクがあるため、Routines運用記事で紹介されたような発火回数の上限設計を併用することが望ましいです。

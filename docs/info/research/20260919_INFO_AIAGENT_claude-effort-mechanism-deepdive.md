# Claude Effortの仕組み詳細:Adaptive Thinkingと3層制御モデル

- **記録日:** 2026-09-19
- **位置づけ:** 「Claude Effortパラメータとは」記事の続編。「ぱっと考えて/じっくり考えて」の塩梅をどう指示するか、その内部仕組み(Adaptive Thinking)と具体的な制御方法を、実例つきで深掘りする。

## 結論:3層構造の制御モデル

```
[Adaptive Thinking] ← Claude自身が「思考するか」を毎回自律判断する土台の仕組み
        ↑
  effortパラメータ  ← その判断の"閾値"を全体的にずらす主要ダイヤル(low〜max)
        ↑
プロンプト誘導(システム/メッセージ単位) ← 特定の会話・特定のやり取りだけ細かく微調整
        ↑
  max_tokens ← 万一の暴走を防ぐ、絶対的な安全弁
```

## 1. 中核パラメータ:`effort`

APIリクエストの`output_config.effort`に文字列で指定する。

```json
{
  "model": "claude-opus-5-5",
  "max_tokens": 4096,
  "output_config": { "effort": "medium" },
  "messages": [{ "role": "user", "content": "..." }]
}
```

5段階あり、「Claudeがどれだけ気軽に・どれだけ深く思考するか」のデフォルト傾向を決める。

| effort | 思考の挙動(公式表現) |
|---|---|
| `max` | 最も気軽に、最大の深さで思考。長さに制約なし |
| `xhigh` | `high`より気軽かつ深く思考。長時間の探索向け |
| `high`(多くのモデルでデフォルト) | 恩恵がある大半のリクエストで思考。複雑タスクで深い推論 |
| `medium`(Opus 5.5のデフォルト) | 中程度の思考。単純な質問は思考をスキップすることも |
| `low` | 思考を最小化。速度優先で単純タスクは思考をスキップ |

**重要:** effortは「思考の"入り口"のダイヤル」であり、実際に思考するかどうかは、Claude自身が毎リクエストごとに個別判断する。どのレベルでも「必ず思考ブロックが付く」保証はない。

## 2. 実際の仕組み:「Adaptive Thinking(適応的思考)」

Claudeは**リクエストの複雑さを自分で評価し、思考するかどうか・どれだけ深く思考するかを都度自分で決める**。この意思決定の仕組みが「適応的思考」。

- 例:「今日は何曜日?」→ 単純な事実質問なので、思考ブロックなしで即座に回答
- 例:「この複雑なバグの原因を特定して」→ 内部で段階的に思考(thinkingブロック)を生成してから回答

effortはこの「思考するかどうかの閾値」を全体的にシフトさせる、いわば**「思考への積極性のバイアス」**として働く。`low`にすると閾値が上がり(簡単な問題は思考をスキップしやすくなる)、`max`にすると閾値が下がる(どんな問題でも積極的に思考する)、というイメージ。

## 3. さらに細かく制御する方法(3段構え)

公式ドキュメントは、以下の優先順位でチューニングすることを推奨している。

**① effortレベルを設定**(基本の姿勢を決める)
```
output_config: { effort: "high" }
```

**② システムプロンプトでの誘導**(会話全体の閾値をずらす)
```
思考を増やしたい場合:
「このタスクは複数ステップの推論が必要です。回答前に慎重に考えてください」

思考を減らしたい場合:
「拡張思考はレイテンシを増やすので、回答品質が明確に向上する場合のみ使ってください。
迷ったら直接回答してください」
```

**③ メッセージ単位での誘導**(その1回のやり取りだけ)
```
ユーザーメッセージの末尾に追記:
「じっくり考えてから答えて」→ その回だけ思考を促す
「考えずに直接答えて」→ その回だけ思考を抑制する
```

実務では、エージェント(自律的にタスクをこなす仕組み)が「計画を立てるステップでは②の誘導フレーズを付け、単純な確認応答ステップでは③の抑制フレーズを付ける」といった、ステップごとの動的な使い分けもできる。

## 4. コストを絶対に超えさせたくない場合:`max_tokens`

effortは**あくまで"ソフトな指針"**であり、厳密な上限ではない。「絶対にこのトークン数を超えさせない」という**ハードな上限**が必要な場合は、`max_tokens`パラメータを使う(思考トークン+応答テキストの合計に対する絶対上限)。

| 制御手段 | 性質 |
|---|---|
| `effort` | ソフトガイダンス(思考の"姿勢"を決める) |
| `max_tokens` | ハードリミット(絶対に超えない上限) |
| システムプロンプト/メッセージ誘導 | 自然言語での促し(文言の表現に敏感、effortほど精密ではない) |

## 5. 具体例で見る、effortレベルによる違い

### 例1:「東京から大阪までの距離は?」(単純な事実質問)

**`low`の場合の内部挙動(イメージ)**
```
[thinkingブロック: なし]
[textブロック]
約400km(新幹線経由の営業キロで約515km)です。
```

Claudeは「これは知識ベースから直接引き出せる、検証不要な単純な事実」と即座に判断し、思考ブロック自体を生成せず、学習済みの知識から直接テキストを出力する。

**`high`/`max`の場合でも実はほぼ同じ**

ここが誤解されやすいポイントだが、**effortを`max`にしても、この質問に対して無理やり長い思考をさせるわけではない**。「Effortは厳密なトークン予算ではなく、行動上のシグナル」という公式の定義通り、**Claude自身が「この問題は思考しても答えの質が上がらない」と判断すれば、`max`でも思考をスキップする**。

effortの違いが「見える」のは、**"思考すべきか微妙なライン"の問題に対してだけ**。例えば「東京から大阪まで、新幹線・飛行機・車それぞれで移動した場合の所要時間とコストを比較して、最も効率的な手段を提案して」のように**複数の変数を比較検討する要素が入った瞬間**、`low`では簡略な回答で済ませようとし、`high`では各手段を順に検討する思考ブロックが生成されやすくなる。

### 例2:「Rustコードのメモリリークの原因を、所有権システムの観点から特定して」(複雑な診断タスク)

このタスクは「単一の答え」ではなく「段階的な推論の積み重ねが必要な診断作業」なので、effortレベルによる差が明確に出やすい。

**`low`の場合の内部挙動(イメージ)**
```
[thinkingブロック: 省略されるか、非常に短い]
思考: コード内でDropが実装されていない箇所を確認...

[textブロック]
`Rc<RefCell<T>>`の循環参照が原因と思われます。
Weak参照への変更を検討してください。
```

「最も典型的なパターン(循環参照)にまず当てはめて、それらしい回答を素早く返す」という振る舞いになりがち。実際のコードを1行ずつ丁寧に追跡せず、パターンマッチ的な直感に頼った回答になりやすいため、実際の原因が典型パターンと違う場合は誤診断のリスクが上がる。

**`high`/`max`の場合の内部挙動(イメージ)**
```
[thinkingブロック1]
思考: まず、このコードの所有権の流れを追う必要がある。
関数process_data内でVec<Item>が生成され、Arc::cloneが
3箇所で呼ばれている。それぞれの参照カウントの増減を追跡しよう。

[thinkingブロック2]
思考: 15行目でitems.clone()しているが、これはArcのクローン
(参照カウント+1)であり、ディープコピーではない。この時点で
所有権は共有されているが、これ自体はリークの直接原因ではない。

[thinkingブロック3]
思考: 一方、28行目のコールバック内でselfをmoveでキャプチャ
しているクロージャが、Rc<RefCell<Node>>をイベントリスナーとして
永続的に保持し続けている。これは典型的な循環参照パターンだが、
念のため他の可能性(スレッド間でのチャネル経由の値の滞留等)も
除外しておこう。

[thinkingブロック4]
思考: チャネルの送信側は全てdropされていることを確認。
やはり28行目のクロージャが根本原因と断定できる。

[textブロック]
15行目のArc::clone自体は問題ありませんが、28行目のイベント
リスナー登録でRc<RefCell<Node>>を強参照(Rc)のまま
クロージャにキャプチャしているため、ノード間で循環参照が
発生しています。該当箇所をWeak<RefCell<Node>>に変更し、
アップグレード時に.upgrade()を呼ぶ形に修正してください。
```

「仮説を立てる→検証する→他の可能性を除外する→結論を出す」という、人間のデバッグ作業に近いプロセスを内部で複数ステップ踏んでから、最終的な回答を生成する。thinkingブロックが複数回に分かれているのは、実際のAPIレスポンスでも1つの応答の中に複数の`thinking`コンテンツブロックが順番に含まれうるという仕様に対応している。

### 2つの例を並べて見える、本質的な違い

| 観点 | `low` | `high`/`max` |
|---|---|---|
| **アプローチ** | パターン認識・直感的な当てはめ | 仮説検証・段階的な除外プロセス |
| **見落としへの耐性** | 典型パターンと違う原因は見逃しやすい | 複数の可能性を洗い出してから絞り込む |
| **トークン消費** | 少ない(数百トークン程度) | 多い(数千〜数万トークンに及ぶこともある) |
| **応答までの時間** | 速い | 遅い(思考ステップの分だけ時間がかかる) |
| **向いている場面** | 定型的な確認作業、サブエージェントの下請けタスク | 初見のバグ調査、複雑な設計判断、金銭が絡む決済処理の検証等 |

## 実務での使い分けの勘所

この使い分けは、AIエージェントの運用にも直結する。

- **「このファイルの中身を教えて」のような単純な参照作業** → `low`相当で十分(軽作業を補助モデルに任せる運用と同じ発想)
- **「このコードのセキュリティ上のリスクを洗い出して」のような、見落としが致命傷になりうる分析作業** → `high`/`max`相当が必須

effortの考え方は、「**タスクの性質によって"直感で即答してよい"か"手順を踏んで検証すべき"かが変わる**」という、人間のデバッグ・思考プロセスそのものをパラメータ化したもの、と理解するのが一番しっくりくる。

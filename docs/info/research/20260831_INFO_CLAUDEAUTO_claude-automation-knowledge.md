## 2. ゼロデイ攻撃対策・セキュリティ運用の自動化

### 「Claude Mythos」がFirefoxの脆弱性271件を単一の評価で発見、Mozillaが修正版をリリース
- 出典: https://pacific-meta.co.jp/magazine/news/146520/
- 内容: Anthropicの最新フロンティアAIモデル「Claude Mythos Preview」を使ったセキュリティ評価で、Mozilla Firefoxの271件の脆弱性が発見され、修正版「Firefox 150」がリリースされたという事例。以前にも「Claude Opus 4.6」による22件の脆弱性発見（うち14件が重大度「高」）という前例があり、今回はその規模が大幅に拡大した形です。
- 便利さ: 「一度の評価で数百件規模の脆弱性を発見」という具体的な数字が、AIによる自動セキュリティ監査の実効性を裏付けています。ゼロデイ攻撃（未修正の脆弱性を悪用する攻撃）が実際に発覚する前に、大規模コードベースを横断的にスキャンして先回りする運用のイメージが掴みやすい事例です。
- 注意点: Mozilla側の報告では「ほぼ誤検知（false positive）がなかった」とされていますが、これは著名OSSプロジェクトが人手によるレビュー体制を整えた上での成果であり、自社導入時には同等のレビュー体制なしに修正パッチを自動適用することは避けるべきです。

## 3. インフラ/クラウドエンジニア・SRE・CI/CD・Playwrightによる自動化

### Claude Code自動タスク完全ガイド｜スケジュール実行で毎週の脆弱性監査を自動化するレシピ
- 出典: https://and-and.dev/blog/claude-code-schedule-automation-guide-2026/
- 内容: Claude Codeのスケジュール実行機能（`/schedule`コマンドやデスクトップアプリの「New task」画面から定期タスクを登録できる仕組み）の使い方を解説したガイド。紹介されているレシピの一つが「毎週月曜9時にnpm audit（Node.jsパッケージの脆弱性監査コマンド）やpip audit（Pythonパッケージ版）を実行し、CRITICAL・HIGH（緊急・重大）の脆弱性があればGitHubのIssueを自動作成する」という運用です。
- 便利さ: 「人が定期的に監査コマンドを叩き忘れる」という運用上のよくある抜け漏れを、スケジュール実行によって仕組みとして解消できる点が実務的です。依存パッケージの脆弱性対応は地味だが継続が重要な作業であり、自動化との相性が良い領域です。
- 注意点: 自動生成されるIssueはあくまで「発見・起票」までであり、修正パッケージへの更新やPR（プルリクエスト）のマージは人間の判断とレビューを経て行う運用にする必要があります。全自動でのマージは依存関係の破壊的変更を見落とすリスクがあります。

### "SREって何やってるの？"をなくす——Claude Routineで活動レポートの自動化
- 出典: https://zenn.dev/dely_jp/articles/18cb5e7cc20fab
- 内容: dely株式会社のSREチームが、Claude Codeのデスクトップアプリ刷新（2026年4月14日発表）と合わせて登場した「Claude Routine」（クラウド上で定期タスクを自動実行する機能）を使い、SREの日々の活動内容を自動でサマリして定期投稿するレポートを構築した事例。既にどこかのツールにまとまっている情報を集約して要約するだけの用途なら低コストで自動化できるという知見が紹介されています。
- 便利さ: SREの働きが社内で見えにくいという「あるある」の課題に対し、既存データソースの範囲内で完結する低コストな自動化から着手した現実的なアプローチが参考になります。新しいデータ収集基盤を作らずに始められる点が真似しやすいポイントです。
- 注意点: 「低コストで自動化できる」のは既存ツールに情報が集約されている場合に限られ、複数システムに情報が分散している組織ではまずデータ集約の仕組み作りが前提になります。

## 4. ベストプラクティス、実際に構築・検証して効果があった手順書/実績

### Claude Cowork企業導入ガイド｜サンドボックスVM・SSO・監査ログの設計
- 出典: https://www.ai-native.jp/blog/claude-cowork-enterprise-security
- 内容: Cowork（Claude Desktop上で動く自律型AIエージェント機能）を企業導入する際のセキュリティアーキテクチャを解説した記事。サンドボックスVM（macOSではApple Virtualization Framework、WindowsではHyper-V上のLinuxが動作する隔離環境）によりホストOSと実行環境を分離する仕組み、SSO（シングルサインオン）・監査ログの設計、Connector（外部サービス連携機能）のデータフロー設計、Plugin（拡張機能）の統制、3フェーズの導入ロードマップまでを扱っています。
- 便利さ: 前週紹介した独立系ブログの記事（Chrome連携リスクに慎重な立場）とは異なり、こちらはサンドボックスVMという技術的な隔離機構に着目しており、「Cowork = ホストOSに直接触れるわけではない」という設計思想を理解する助けになります。導入フェーズを分けて進める考え方も、いきなり全社展開しない現実的な計画作りの参考になります。
- 注意点: サンドボックスVMによる隔離があっても、Connector経由で連携した外部サービスのデータ自体は保護対象外のため、どのSaaSと連携させるかの選定・権限スコープの絞り込みは別途必要です。

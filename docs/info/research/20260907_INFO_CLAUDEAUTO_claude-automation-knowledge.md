## 1. ITインフラ/サーバ運用保守のルーティンワーク自動化（Excel特化）

### Claude CodeでExcelレポートを自動生成する方法｜openpyxlで集計・グラフ・書式設定まで一括処理
- 出典: https://funnel-ai.jp/media/claude-code-excel-report/
- 内容: Claude Codeにopenpyxl（既存Excelファイルの読み込み・編集ができるPythonライブラリ）とxlsxwriter（新規Excelファイル作成専用のライブラリ）を使い分けさせ、集計・グラフ生成・書式設定までを一括処理する手順を解説した記事。既存の社内テンプレートに書き込む運用ならopenpyxl、ゼロから高品質なグラフを作る場合はxlsxwriterが向いているという使い分けの判断基準が示されています。
- 便利さ: 「どちらのライブラリを選べばよいか」という最初の疑問に具体的な判断軸を与えてくれる点が実務的です。既存のExcelテンプレートを崩さずに集計欄だけを自動更新したい担当者にとって、選択を誤らないための入口として役立ちます。
- 注意点: どちらのライブラリもExcelの全機能（ピボットテーブルの動的更新やマクロ連携など）を完全にはカバーしないため、複雑な既存ブックへの書き込みでは事前に手動での動作確認が必要です。

## 2. ゼロデイ攻撃対策・セキュリティ運用の自動化

### Claude Code Securityとは？コード脆弱性を自動検出する仕組み【完全ガイド】
- 出典: https://jinrai.co.jp/en/blog/2026/03/26/claude-code-security/
- 内容: Anthropic公式のセキュリティ診断機能「Claude Code Security」（2026年2月に研究プレビュー開始、4月30日にpublic beta化）の仕組みと、既存のルールベース型ツール（SonarQube、Snykなど）との使い分けを解説した記事。CI/CD（継続的インテグレーション/継続的デリバリー、コード変更のたびに自動でビルド・テスト・診断を行う仕組み）ではSonarQubeやSnykでベースラインスキャンを行い、コードレビュー時にClaude Code Securityで文脈を理解した深堀り分析を行うという「2層構造」の運用が推奨されています。
- 便利さ: 「AIツールか既存ツールか」の二択ではなく、両方を役割分担させる具体的な設計指針が示されている点が実務的です。ルールベースツールが検出しにくいビジネスロジックの欠陥（例: 認可チェックの抜け漏れ）をAIが補うという住み分けは、他のセキュリティ自動化にも応用が効く考え方です。
- 注意点: Claude Code Securityはあくまで既存ツールの代替ではなく補完であるため、「AIを導入したから既存の脆弱性スキャンをやめる」という判断は推奨されていません。二重のスキャン体制を維持するコストは事前に見込んでおく必要があります。

### Claude Code --restrictedモード解説｜AIエージェントのCI/CDリスクとAnthropicの回答
- 出典: https://and-and.dev/blog/claude-code-restricted-mode-ci-security-2026/
- 内容: 2026年8月に追加された`--restricted`フラグ（Claude Codeの実行時にファイルアクセスやコマンド実行の権限を制限するモード）を解説した記事。Black Hat USA 2026（世界的なセキュリティカンファレンス）で実証されたCI/CDパイプラインでの秘密鍵漏洩リスクを踏まえ、AIエージェントを自動化パイプラインに組み込む際の安全な設定方法が紹介されています。
- 便利さ: AIエージェントによる自動化を推進する一方で「攻撃対象領域が広がる」という副作用に正面から向き合った実践的なガイドです。CI/CDにClaude Codeを組み込みたいが秘密鍵の扱いに不安がある、という導入検討段階の懸念に具体的な対策を提示しています。
- 注意点: `--restricted`モードは権限を絞る分、一部の自動化タスク（外部APIとの連携など）が動作しなくなる可能性があるため、導入前に自社のワークフローで必要な権限の棚卸しが必要です。

## 3. インフラ/クラウドエンジニア・SRE・CI/CD・Playwrightによる自動化

### QAエンジニアがClaude Codeを半年間使って気づいたこと〜テスト自動化74%高速化を実現した3つの技術アプローチ〜
- 出典: https://www.m3tech.blog/entry/2026/04/20/090035
- 内容: エムスリー株式会社のQAエンジニアが、Claude Codeを半年間活用してPlaywrightによるE2Eテストを構築した事例。テスト実行時間を74%短縮（既存ツール105分→Playwright 27分）し、年間約68時間分のCI/CD待ち時間を削減、67件のMR/PR（マージリクエスト/プルリクエスト）をマージしたという定量的な実績が報告されています。
- 便利さ: 「導入したら早くなった」という定性的な感想ではなく、実行時間・削減時間・マージ件数という具体的な数字で効果を示している点が、社内稟議や投資対効果の説明に使いやすい実績データです。半年間という一定期間の継続活用を経た知見であるため、初期の勢いだけでない持続的な効果として参考になります。
- 注意点: 効果の大きさは既存のテストツールの実行速度がボトルネックになっていた組織ほど顕著に出やすく、既にテスト基盤が最適化されている環境では同等の削減率が出るとは限りません。

### Claude Code と Playwright MCP を用いたE2Eテスト自動化スキルの構築
- 出典: https://recruit.group.gmo/engineer/jisedai/blog/claude-code-playwright-e2e-test-automation/
- 内容: GMOインターネットグループの研究開発部門が、Playwright MCP（Model Context Protocol、AIエージェントが外部ツールを呼び出すための標準規格）を使ったE2Eテスト自動化を構築した事例。「テストコードを書かず自然言語の計画で動作確認を自動化する」という方針転換により、簡単な修正の動作確認をClaudeにほぼ任せ、issue/PRの差分を読んで計画立案から実行まで行わせる仕組みを目指しています。
- 便利さ: 「テストコードを書く」から「自然言語で確認内容を指示する」への発想転換が紹介されており、E2Eテストのメンテナンスコスト（画面変更のたびにテストコードを直す手間）に悩む現場にとって別のアプローチの選択肢を示しています。
- 注意点: 自然言語ベースのテストは再現性・厳密性の面でコード化されたテストに劣る場合があり、証跡（実行ログやスクリーンショット）を残す設計を別途組み込む必要がある点が記事内でも言及されています。

### AIにシステム月次レポートを書かせる ── Claude Code × MCPで運用レポートを自動生成する
- 出典: https://kenzo0107.github.io/2026/06/10/2026-06-11-ai-system-monthly-report/
- 内容: 個人エンジニアが、Claude CodeとMCP（外部データ取得の標準規格）を組み合わせて各サービスの月次運用レポートを自動生成する仕組みを構築した実践記。レポート末尾に必ず「作成者: AI (Claude Code) + SRE確認」と明記し、AIが下書きを作り人間が確認して締めるというワークフローを明示している点が特徴です。
- 便利さ: 「AIが全部やる」のではなく「AIが下書き、人間が確認」という役割分担を、レポートの表記上にも残すという運用の型が具体的で真似しやすいです。責任の所在を明確にしたい社内文書の自動化全般に応用できる考え方です。
- 注意点: この事例は個人が試行した範囲の構築であり、組織規模での運用には承認フローや監査ログの整備など追加の統制が必要になります。

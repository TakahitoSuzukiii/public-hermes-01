## 1. ITインフラ/サーバ運用保守のルーティンワーク自動化（PPT資料・Excelレポート作成）

### PowerPoint自動生成でAIにデザインさせるのをやめた：Claude Code × python-pptxで「自分が手作業で作るスライド」を再現する
- 出典: https://techblog.insightedge.jp/entry/powerpoint-auto-generation
- 内容: データサイエンティストが、PowerPoint自動生成で「AIが作った感」が出てしまう問題に対し、デザイン判断そのものをAIから取り上げる設計にたどり着いた事例です。python-pptx（既存の.pptxを操作できるPythonライブラリ）を使った自作ヘルパー関数（表作成・見出し配置・分割レイアウトなど）に配色・罫線・フォント・余白を全てハードコードし、Claude Codeの役割を「どの関数を、どのデータで呼ぶか」だけに限定しています。
- 便利さ: OOXML（PowerPointファイルの実体であるXML形式）直接編集・画像生成・HTML生成という3方式を試した上での失敗談が具体的で、「デザインルールを自然言語プロンプトで守らせようとした」ことが全ての失敗の共通原因だったという振り返りは、他の自動化設計にも応用できる教訓です。修正も「いつもの自分の操作」でそのまま直せる再現性の高さが評価点です。
- 注意点: ヘルパー関数側に自社の「承認済みデザイン」を先に定義しておく前工程が必要で、既存テンプレートが定まっていない組織ではまずフォーマットの標準化から着手する必要があります。

### Claude Codeで毎週3時間削減！Excelの集計・レポート作成を完全自動化した話
- 出典: https://generative-ai.co.jp/claude-code/claude-code-spreadsheet-automation-excel-workflow/
- 内容: プログラミング未経験者が、Claude Codeを使い「簡単な合計・平均計算」→「複数支店ファイルの統合」→「グラフ付き週次レポート生成」と段階的にステップアップし、1ヶ月間の実運用で週3時間（年間150時間相当）の削減を達成した体験記です。エラーが出てもエラーメッセージをそのままClaude Codeに見せて解決できた点を「挫折しない安心材料」として強調しています。
- 便利さ: 非エンジニアが実際に手を動かした一次体験として、「最初は簡単な作業から試す」という導入順序がそのまま参考になります。日本語の列名でエラーになった際の対処など、実務でつまずきやすい具体的なポイントも含まれています。
- 注意点: 本記事は個人の体感ベースの記録であり、効果の再現性（データ規模やファイル形式の違いによる差）は限定的です。前週号（9/21号）で紹介した第三者による同種の再検証記事とあわせて読むと、効果の妥当性をより多角的に判断できます。

## 2. ゼロデイ攻撃対策・セキュリティ運用の自動化

### Claude Securityとsecurity-guidanceで開発初期から脆弱性対策を自動化
- 出典: https://recruit.group.gmo/engineer/jisedai/blog/claude-security-early-vulnerability-automation/
- 内容: GMOインターネットグループ グループ研究開発本部が、リリース前・開発初期の2リポジトリ（合計約29万行、JWT認証・複数組織データ分離・LLM連携・メディアストリーミングを抱える攻撃面の広いシステム）に対し、Claude Security（Anthropic公式のClaude Codeプラグイン）でフルスキャンを実施した事例。Inventory（棚卸し）→Threat model（脅威モデル化）→Research（調査）→Sweep（補完調査）→Panel（独立した検証者3体による合議）という5フェーズのマルチエージェント構成で、誤検知を抑えながら72件の脆弱性を検出しています。
- 便利さ: 実時間（約2時間+約3.5時間）・トークン消費（約16.5億）・API定価換算費用（約$1,715、実際はMaxプラン定額のため実質0円）・パッチ9本が人間レビューで却下された理由まで、実測値を包み隠さず公開している点が非常に貴重です。「自動コミット・自動PRは禁止し、パッチファイルを人間が確認してgit apply する」という運用は、AGENTS.mdのHITL（Human-in-the-Loop）原則ともそのまま合致します。
- 注意点: この効果は「第三者監査を控えたリリース前」という前提で測定されたものであり、本番稼働中システムへの適用や、コンポーネント数の少ない小規模プロジェクトでは所要時間・費用感が大きく変わる可能性があります。

## 3. インフラ/クラウドエンジニア・SRE・CI/CD・Playwrightによる自動化

### Claude CodeとPlaywright MCPで実現する対話型UI自動テスト構築
- 出典: https://dev.classmethod.jp/articles/building-interactive-ui-tests-with-claude-code-and-playwright-mcp/
- 内容: クラスメソッドが、「セレクタを探す→失敗する→ブラウザを見直す」という往復作業を解消するため、Claude CodeとPlaywright MCPを組み合わせた対話型UIテスト構築手法を紹介した事例。Claude Codeがブラウザを実際に操作して画面表示・要素情報・スクリーンショットを確認した上でテスト候補を提示し、人間が承認してからテストコードを生成する、という「確認作業とテスト作成を分断しない」流れが特徴です。
- 便利さ: テストコードを書く前に「何をテストするか」を人間とAIで対話的に合意するプロセスにより、動かないテストを書いてしまう手戻りが減る点が実務的です。DevelopersIOのハンバーガーメニューのテスト構築を実例に、生成されたテストコードまで公開しており、そのまま模写して試せる完成度です。
- 注意点: 本記事は個別修正の事後確認的なテスト構築に主眼があり、前週号（9/21号）で紹介したGMOグループの「回帰スイートは従来型コード、探索的確認は自然言語エージェント」という使い分けの整理とあわせて読むことで、導入範囲の判断がしやすくなります。

## 4. ベストプラクティス、実際に構築・検証して効果があった手順書/実績

### Claude Codeではじめる、インフラ構築/運用 ── IaC編（再掲・継続参照推奨）
- 出典: https://zenn.dev/nocall/articles/09534c8b6832a2
- 内容: 音声AI SaaS「nocall」が、AWSインフラをClaude CodeとTerraform（インフラ構成をコードで管理するツール）で構築した実践記です。検証環境では`terraform apply`（実適用）までClaude Codeに任せる一方、本番環境は`plan`（差分確認のみ）に権限を制限し、適用は必ず人間が行うという環境分離を徹底しています。
- 便利さ: 9/21号でも触れましたが、今週紹介するセキュリティ運用記事（GMOグループ）の「自動コミット禁止・人間レビュー必須」という設計思想と根が同じであり、「AIエージェントにどこまで任せるか」をアカウント・環境単位で線引きするパターンが業種を超えて再現されている点に注目したく、今週も踏まえて再掲しました。
- 注意点: Terraformの網羅的導入（既存の手動作成リソースの巻き取り）が前提となるため、IaC化が進んでいない組織ではまず棚卸しという地道な準備工程が必要です。

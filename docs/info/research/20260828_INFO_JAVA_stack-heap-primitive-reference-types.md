# スタックとヒープ、プリミティブ型・参照型の違い

> Java(などのオブジェクト指向言語)における、変数の保存先(スタック/ヒープ)と、プリミティブ型・参照型の挙動の違いをまとめる学習ノート。

## 0. 結論(先出し)

```
int n = 5;            → スタックに「5」そのものが入る
User u = new User();  → スタックには「9000番地」という住所だけが入る
                         実体(Userオブジェクト)はヒープの9000番地にある
```

**「プリミティブ型は実体そのものがスタックに乗る」「それ以外(参照型/オブジェクト)はヒープに実体があり、スタックには住所(参照)だけが乗る」** — これが核心。

## 1. なぜこの仕組みになっているのか

| 観点 | プリミティブ型(int, boolean, char等) | 参照型(オブジェクト、配列、Stringなど) |
|---|---|---|
| **サイズ** | 決まったサイズ(intなら4バイト等)で固定 | サイズが可変(オブジェクトの中身は増減しうる) |
| **保存場所** | スタック | ヒープ(実体) + スタック(住所のみ) |
| **理由** | サイズが決まっているので、スタックのような「積み上げ式」の高速な領域にそのまま置ける | サイズが不定・大きくなりうるものは、スタックのような制限された領域には向かない。ヒープという自由に確保できる広い領域に置き、スタックには「どこにあるか」の住所(ポインタ/参照)だけを持たせる |

## 2. スタックとヒープ、それぞれの性質

**スタック(Stack)**
- 「後入れ先出し(LIFO)」の構造。メソッドが呼ばれるたびに、その中のローカル変数用の領域が積まれ、メソッドが終わると自動的に消える
- アクセスが非常に高速
- サイズに上限がある(積みすぎるとスタックオーバーフロー)

**ヒープ(Heap)**
- 自由に確保・解放できる広い領域
- `new`でオブジェクトを作ると、ここに実体が作られる
- スタックより自由度が高い分、アクセス速度はやや遅い
- 誰からも参照されなくなったオブジェクトは、ガベージコレクション(GC)が自動的に片付ける

## 3. 具体例で動きを追う

```java
int n = 5;
User u = new User();
```

1. `int n = 5;` → スタックのあるアドレスに、値「5」がそのまま書き込まれる
2. `User u = new User();` → まずヒープ上にUserオブジェクトの実体が作られる(住所: 9000番地と仮定) → スタックの別のアドレスには「9000」という**住所だけ**が書き込まれる

## 4. この違いが引き起こす「あるある」現象

### ① 代入の挙動が違う

```java
int a = 5;
int b = a;   // aの「値」がコピーされる → bは独立した5
b = 10;      // aには影響なし(aは5のまま)

User u1 = new User();
User u2 = u1;  // u1の「住所」がコピーされる → u2もu1も同じ実体(9000番地)を指す
u2.setName("鈴木"); // u1.getName()も"鈴木"になる(同じ実体を見ているため)
```

これが「プリミティブ型は値渡し、参照型は(参照の)値渡しだが実質オブジェクトを共有する」と言われる理由。

### ② メソッドに渡したときの挙動

```java
void changeValue(int x) { x = 100; }        // 呼び出し元のnには影響なし
void changeUser(User u) { u.setName("A"); } // 呼び出し元のUserの中身が変わる(同じ実体を指しているため)
```

## 5. 覚え方

- **プリミティブ = 実体そのものがそこにある**
- **参照型 = そこにあるのは「住所」だけ、実体は別の場所(ヒープ)にある**

**慣れないうちは、スタック表とヒープ表を必ず両方書く**のが実践的な学習法。バグの多くは「参照を共有していることに気づかず、片方を変えたらもう片方も変わってしまった」というパターンから生まれるため、この基礎理解はデバッグ力に直結する。

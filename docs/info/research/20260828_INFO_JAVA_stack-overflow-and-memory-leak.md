# スタックオーバーフローとメモリリーク

> 前回の学習ノート([スタックとヒープ、プリミティブ型・参照型の違い](20260828_INFO_JAVA_stack-heap-primitive-reference-types.md))の続編。スタック領域・ヒープ領域それぞれで発生する代表的な問題「スタックオーバーフロー」「メモリリーク」を整理する。

## 0. 結論(先出し)

| | スタックオーバーフロー | メモリリーク |
|---|---|---|
| **発生する領域** | スタック領域 | ヒープ領域 |
| **典型的な原因** | 再帰呼び出しが深すぎる/無限に続く | 使い終わったオブジェクトへの参照が残り続け、GCが回収できない |
| **症状の出方** | 即座に強制終了(StackOverflowError等) | 徐々にメモリ使用量が増え続け、最終的にOutOfMemoryError等で落ちる |

両方とも「メモリ不足でプログラムが落ちる」という点は共通するが、**原因の場所(スタックかヒープか)と、発生の速度(瞬間的か、じわじわか)が違う**。

## 1. スタックオーバーフローとは

### 1-1. 仕組み

スタックは「後入れ先出し(LIFO)」の領域で、メソッドが呼ばれるたびにその実行に必要な情報(スタックフレーム)が積まれる。スタック領域にはOSやJVM(Javaの実行環境)によって上限サイズが決められており、**この上限を超えて積み続けるとスタックオーバーフローが発生**する。

出典: [aetheria.jp「スタックオーバーフローって何が起きてるの？」](https://aetheria.jp/4118/)

### 1-2. 主な原因

1. **無限再帰**: 終了条件がない、または誤っている再帰呼び出し
2. **深すぎる再帰**: 終了条件はあるが、再帰の深さがスタックの上限を超えてしまう(例: 巨大なデータに対する再帰処理)
3. **相互参照(相互再帰)**: メソッドAがメソッドBを呼び、BがまたAを呼ぶ、という循環
4. **巨大なローカル変数**: 1回のメソッド呼び出しで消費するスタック領域が大きすぎる

出典: [code.aetheria.jp「java.lang.StackOverflowErrorの原因と解決方法」](https://code.aetheria.jp/1629/)

### 1-3. 具体例(Java)

```java
// 悪い例: 終了条件がない無限再帰
void loop() {
    loop(); // 自分自身を呼び続ける → いずれStackOverflowError
}
```

### 1-4. 対策

- 再帰処理には**必ず終了条件**を設ける
- 再帰の深さが予測できない/大きくなりうる場合は、**ループ(反復処理)に書き換える**
- どうしても深い再帰が必要な場合は、スタックサイズの上限をJVM起動オプション等で拡張する(根本対策ではなく応急処置)

## 2. メモリリークとは

### 2-1. 仕組み

Javaのようにガベージコレクション(GC)を持つ言語では、「どこからも参照されなくなったオブジェクト」はGCが自動的にヒープから回収してくれる。**メモリリークとは、本来不要になったはずのオブジェクトへの参照がどこかに残り続け、GCが回収できずにヒープ上に居座り続けてしまう現象**を指す。

C言語のような手動メモリ管理の言語における「解放し忘れ」とは異なり、GCがある言語のメモリリークは**「意図せず参照が残っている」ことが原因**という点が特徴。

出典: [Qiita「"見えてるけど見えてない"メモリリークの実体」](https://qiita.com/K3n_to_n17/items/cbd8f1022c37371d6e52)

### 2-2. 主な原因(GCがある言語での典型例)

1. **静的(static)フィールド/コレクションへの追加し忘れ削除**: `static List`等にどんどん要素を追加し、不要になったものを削除しない
2. **リスナー/コールバックの登録解除忘れ**: イベントリスナーを登録したまま解除しないと、参照が残り続ける
3. **キャッシュの無制限増加**: キャッシュとしてMapに保存し続け、有効期限や上限を設けない
4. **内部クラス(無名クラス等)による暗黙の参照**: 内部クラスが外部クラスへの参照を暗黙に持ち続けるケース

### 2-3. 症状の出方

スタックオーバーフローが「瞬間的に発生してすぐ落ちる」のに対し、メモリリークは**時間をかけてじわじわとメモリ使用量が増加**し、最終的にヒープの上限に達すると`OutOfMemoryError`等でプログラムが異常終了する。サーバーアプリケーションのように長時間稼働し続けるプログラムで特に問題になりやすい。

### 2-4. 対策

- 不要になったオブジェクトへの参照を明示的に断つ(nullを代入する、コレクションから削除する等)
- リスナー登録には必ず解除処理をセットで書く
- キャッシュには上限・有効期限を設ける(またはWeakReference等、GCの対象になりやすい参照方式を使う)
- プロファイリングツール(Javaならヒープダンプ解析ツール等)でメモリ使用量の推移を定期的に観察する

## 3. 2つの違いのまとめ

| 観点 | スタックオーバーフロー | メモリリーク |
|---|---|---|
| 発生領域 | スタック | ヒープ |
| 主な原因 | 再帰の深さ・回数の制御ミス | 不要な参照の残存 |
| 発生スピード | 即座(数秒〜数十秒以内) | 徐々に(数時間〜数日かけて) |
| 気づきやすさ | エラーで即座に気づく | じわじわ進行するため気づきにくい |
| 主な対策 | 終了条件の徹底、ループへの書き換え | 参照管理の徹底、プロファイリング |

出典: [teratail「メモリリークとスタックオーバーフローの違い」](https://teratail.com/questions/150637)、[Lab AI「スタックとヒープ」](https://lab.main.jp/ai/posts/memory-stack-heap/)

## 4. 学習のポイント

前回のノートで扱った「スタック=プリミティブ型の実体、ヒープ=参照型の実体」という基礎理解があると、この2つの問題も整理しやすい。

- **スタックオーバーフロー**は「積みすぎ」の問題 → **メソッド呼び出しの深さ**をコントロールする話
- **メモリリーク**は「片付け忘れ」の問題 → **オブジェクトへの参照**をコントロールする話

どちらも「使い終わったら適切に手放す」という意識が根本的な対策になる点は共通している。

# OLTP/OLAPの違い、トランザクションDBの本質、トランザクションログ(WAL)を理解する

作成日: 2026-09-04 / STATUS: INFO / TOPIC: DATABASE

> 前回記事「DuckDBに類似・関連する分析基盤・DB群の全体マップ」の発展として、OLTP/OLAPの違いと、MySQL・PostgreSQLがなぜ「トランザクションDB」と呼ばれるのかを、アプリ・インフラの設計観点も交えて整理する。

---

## 1. OLTP vs OLAP — 何が違うのか

### 一言でいうと

| | OLTP | OLAP |
|---|---|---|
| 正式名称 | Online Transaction Processing（オンライントランザクション処理） | Online Analytical Processing（オンライン分析処理） |
| 目的 | **日々の業務データを正確に記録・更新する** | **蓄積したデータを集計・分析して洞察を得る** |
| 典型的な処理 | 「注文を1件登録する」「在庫を1個減らす」 | 「先月の地域別売上合計は？」「過去1年のユーザー継続率は？」 |
| 1回の処理が触るデータ量 | 少ない（数行） | 膨大（数百万〜数億行） |
| 読み書きの比率 | 書き込みが頻繁 | ほぼ読み込み専用（集計） |
| データの構造 | **行指向**（1レコード＝1注文、のように横に並ぶ） | **列指向**（「金額」列だけを大量に集計する等） |
| 代表例 | MySQL, PostgreSQL, Oracle | Snowflake, BigQuery, Redshift, DuckDB |

### なぜ「行指向 vs 列指向」が本質的に重要か

**OLTP（行指向）のイメージ:** ECサイトの注文テーブルがあるとして、「注文ID:1001、商品:マウス、金額:2000円、日付:2026-09-04」という**1行（1レコード）全体**をディスク上に連続して保存する。「注文1001の詳細を1件取得・更新する」という処理が高速。

**OLAP（列指向）のイメージ:** 「先月の金額の合計を出したい」という時、行指向だと1000万件の注文レコードを1件ずつ全部読んで、そこから「金額」の値だけを拾い出す必要があり非常に遅い。列指向は最初から「金額」という**列だけをまとめて連続保存**しているので、その列だけをドサッと読んで合計すれば済み、圧倒的に速くなる。

一方、列指向は「注文1001の全項目を1件だけ更新する」のは逆に不得意（色々な列に散らばって書き込む必要がある）なので、OLTPには向かない。

## 2. なぜMySQL・PostgreSQLは「トランザクションDB」と呼ばれるのか

### トランザクションとは何か

「トランザクション」とは、**複数の処理を『まとめて1つの操作』として扱う仕組み**である。銀行振込が定番の例である。

> Aさんの口座から1万円を引く ＋ Bさんの口座に1万円を足す

この2つの処理は、**両方成功するか、両方失敗するか**のどちらかでなければいけない。「Aさんから引いたのに、Bさんに入金される前にシステムが落ちた」となると1万円が消滅してしまう。これを防ぐのがトランザクションである。

### ACID特性という設計原則

MySQL・PostgreSQL等の「RDB（リレーショナルデータベース）」がトランザクションDBと呼ばれる所以は、**ACID**という4つの性質を保証する設計になっているからである。

| 頭文字 | 意味 | 平易に言うと |
|---|---|---|
| **A**tomicity（原子性） | トランザクション内の処理は全部成功か全部失敗のどちらか | 「振込の一部だけ成功」は絶対に起きない |
| **C**onsistency（一貫性） | トランザクション前後でデータの整合性ルールが必ず守られる | 残高がマイナスになる、といった矛盾したデータにならない |
| **I**solation（独立性） | 同時に複数のトランザクションが走っても、互いに干渉しない | 他の人の処理途中の中途半端な状態が見えない |
| **D**urability（永続性） | トランザクションが成功したら、その結果は絶対に失われない（電源が落ちても） | 「振込完了」と表示された後にサーバーがクラッシュしても、その結果はディスクに残っている |

OLAP系のDWH（データウェアハウス）は、こうした「同時多発する細かい書き込みの整合性」を厳密に保証する必要がない（基本は分析用の読み込み専用）ため、ACIDを緩めて、その分「大量データの読み込み速度」に全振りした設計になっている。これが「トランザクションDB」と呼ばれない理由である。

## 3. トランザクションログ（WAL）とは何か、なぜ重要か

### 仕組み:「先に記録してから、実際の反映をする」

RDBがACIDの中でも特に**D（永続性）**を実現するための仕組みが「**トランザクションログ**」（PostgreSQLでは**WAL: Write-Ahead Log、先行書き込みログ**と呼ばれる）である。

考え方はシンプルである:

1. データを実際のテーブル（データファイル）に書き込む前に、まず「**これから何をするか**」という変更内容を、**専用のログファイルに追記**する
2. ログへの書き込みが完了して初めて「トランザクション成功」と応答する
3. 実際のテーブルへの反映（ディスク上のデータファイル更新）は、その後にまとめて（非同期で）行われる

### なぜこれが重要か（クラッシュリカバリの仕組み）

もしデータベースサーバーが、テーブル本体への反映が終わる前に**突然クラッシュ**したとする。この時、電源復旧後にデータベースは以下のように振る舞う:

- **ログには記録されているが、テーブルにはまだ反映されていない変更がある** → 起動時にログを読み直して、**その変更を再実行（redo）**する。これにより「成功したはずの処理」は必ず反映される。
- **ログにすら記録されていない（＝応答を返す前にクラッシュした）変更** → そもそも「成功した」とアプリ側にも伝わっていないので、なかったことにしてよい。

つまり、**「先にログにさえ書いておけば、後からいつでも復元できる」**という保険の仕組みである。これが「トランザクションログ」の本質的な役割である。

### なぜ「先に」書くのが速いのか

一見、「ログに書いて、さらにテーブルにも書く」のは二度手間に見えるが、実は理にかなっている。

- ログへの書き込みは**シーケンシャル書き込み**（ディスクの決まった位置に順番に追記していくだけ）なので、非常に高速
- 実際のテーブルデータへの反映は**ランダム書き込み**（データが色々な場所に散らばっている）になりがちで遅い

なので「速いログにまず書いて即座に成功を返し、遅いテーブル反映は裏でゆっくりやる」という設計にすることで、**ユーザーへの応答速度**と**データの安全性**を両立させている。

## 4. アプリ・インフラ設計の観点から見た実務的な意味合い

### アプリ設計への影響

- **トランザクション境界の設計が重要:** 1つのトランザクションに詰め込みすぎると、ロック（他の処理を待たせる仕組み）が長時間発生し、パフォーマンスが悪化する。逆に細かく分割しすぎると、途中で失敗した時の整合性維持が難しくなる。「振込処理はまとめる」「大量バッチ処理は小分けにコミットする」等の設計判断が必要になる。
- **リトライ設計:** ネットワーク断等でトランザクションの成否が分からない時、アプリ側は「べき等性（同じ処理を2回やっても結果が変わらない仕組み）」を意識した設計が求められる。

### インフラ・運用設計への影響

- **WAL（トランザクションログ）はディスク容量・I/O設計に直結:** 書き込みが多いDBは、WALの出力量も比例して増える。**専用の高速ディスク（SSD）をWAL領域に割り当てる**、というインフラ設計判断はPostgreSQL運用の定石。
- **バックアップ・リストアの基盤になる:** 「フルバックアップ＋それ以降のWALを全部保持」しておけば、**任意の時点にピンポイントで復元（PITR: Point-In-Time Recovery）**できる。システムリプレース・移行案件でも重要な概念になる。
- **レプリケーション（複製）の仕組みそのもの:** PostgreSQLのレプリケーション（マスター・レプリカ構成）は、実は「WALを別サーバーに転送して、そこで再生する」ことで実現している。障害対策・読み取り負荷分散のインフラ構成を理解する上での基礎になる。
- **DR（災害対策）設計:** WALをリアルタイムで遠隔地に転送しておけば、メインのデータセンターが丸ごと落ちても、直前の状態まで復元できる。

## まとめ

- **OLTP＝正確に記録する仕組み（行指向・ACID重視）、OLAP＝大量に分析する仕組み（列指向・速度重視）**という設計思想の違い
- MySQL・PostgreSQLが「トランザクションDB」と呼ばれるのは、**ACID特性を保証する設計だから**
- トランザクションログ（WAL）は「**先に軽い記録をしてから、重い反映は後で行う**」という仕組みで、速度と安全性（クラッシュ後の復元）を両立している
- この仕組みは、アプリの整合性設計だけでなく、**バックアップ・レプリケーション・DR設計といったインフラ全般の基盤**にもなっている

# 「Rust経験者がZigを試した感想」を読む — What Zig felt like, coming from Rust

- **記録日:** 2026-09-19
- **位置づけ:** Hacker Newsで275pt・345コメントと大きな反響を集めた記事「What Zig felt like, coming from Rust」(besok氏、2026-08-14)を調査・要約。7年間のRust開発者が、同じJSONPathライブラリをZigで再実装して得た一次体験に基づく比較記事。Rustシリーズおよび Zig(新興の低レベル言語)の入門的位置づけも兼ねる。

## 検証方法:同じものを両言語で作る「フェアな比較」

著者は7年間Rustを使ってきた開発者(OSS活動中心)。**公平な比較にするため、既にRustで実装済みのJSONPath(JSON文書に対するクエリ言語、RFC 9535で規定)ライブラリ「jsonpath-rust」を、Zigで再実装**した(`zig-jsonpath`)。おもちゃレベルの練習ではなく、実際にコミュニティで使えるレベルのものを選んでいる点がこの記事の信頼性を高めている。

## 1. IDEサポート:最初の驚き

Rustでは`RustRover`のような高機能IDEを使っていたが、**Zigは構文ハイライトと基本的な自動補完程度しかサポートがない**ことに驚いたという。ただしこれは弱点というより、**CLIツールに素直に頼る開発スタイルへの回帰**という発見にもつながり、著者はこの経験をきっかけに`helix + alacritty + zellij`という軽量な開発環境へ移行した。

`build.zig`(Zigのビルド設定)は非常に扱いやすく、以下のようなコマンド体系が組めたという。

```
zig build test                              # 全テスト実行
zig build test -Dfilter="filter match ..."  # 特定テストのみ
zig build compliance                        # 準拠テストスイート
zig build check                             # ユニットテスト+準拠テスト
```

## 2. フラットな構造への誘導

Rustでは、ファイルサイズとフォルダの階層深さのバランスを常に悩みながら決めていたが、**Zigは(Cのように)フラットな構造を自然に促す言語**だと感じたという。

- ネスト(入れ子)構造も可能だが、import時の摩擦が増えるため、「わざわざ分ける意味があるか?」と自問することになる
- 結果として、著者のZig版プロジェクトは最後まで**深いフォルダ階層が一切不要**だった

**Rust版のディレクトリ構造(抜粋):**
```
src/
├── lib.rs
├── parser.rs
├── parser/
│   ├── errors.rs
│   ├── macros.rs
│   └── ...
└── query/
    ├── atom.rs
    ├── comparable.rs
    └── ...(11ファイル)
```

**Zig版のディレクトリ構造:**
```
src/
├── root.zig
├── parser.zig
├── model.zig
├── model_query.zig
└── query.zig
```

この対比を通じて著者は、「フォルダ構造を分けるのは、本当にプロジェクトの規模上必要だからか、それとも単なる習慣か」を見直すきっかけになったと述べている。

## 3. テストの書きやすさ:Rustに軍配

Rustでは「同じファイル内のインラインユニットテスト」と「独立した`tests`フォルダの結合テスト」という2パターンを使い分けていたが、Zigでは**フラットな構造ゆえに冗長になりがち**だったという。最終的に`build.zig`で明示的に設定する形に落ち着いたが、**「テストの書き心地・管理のしやすさは、総じてRustの方が上」**というのが著者の評価。ただし著者自身、この差は**テスト基盤自体の違いというより、Zigの手動メモリ管理に起因する副次的な摩擦**だと分析している。

## 4. 関数型パラダイムの不在

Rustは技術的には命令型言語だが、ゼロコストイテレータ・遅延評価・代数的データ型・パターンマッチ・モナド的な型・トレイト・クロージャなど、**関数型の概念を色濃く取り入れている**。著者自身もHaskell・Erlang経験があり、関数型スタイルを好む。

Zigに移植する際、**この関数型的な設計思想の多くを持ち込めなかった**という。

| 観点 | Rust | Zig |
|---|---|---|
| 型システムでの多態性 | トレイト(コンパイル時に検証される契約) | ダックタイピング(`@hasDecl`でメソッドの存在だけ確認、コンパイル時の型契約はない) |
| データ変換 | 不変(immutable)な変換、`flat_map`等のコンビネータ | インプレースな破壊的変更(ミューテーション)が中心 |
| ループ処理 | `.iter().filter().map().collect()`のような宣言的コンビネータ | `while`ループによる手続き的な記述 |

著者は「**それぞれの言語の設計目標・対象領域を反映した妥当なトレードオフ**」としつつも、「**主観的には、出来上がったZigのコードはRust版より読みやすさで劣った**」と率直に述べている。

## 5. アロケータ:Zigの核心にして最大の負担

Zigでは**ほぼ全ての関数がアロケータを受け取り、ほぼ全ての構造体がアロケータを保持する**。これはZigの言語設計そのものの核心であり、覚悟していたことではあるが、**実際にやってみると地道で骨が折れる作業**だったという。

- `init`/`deinit`の対応関係を、常に手動で几帳面に守り続ける必要がある
- コールスタックが深くなるほど、この規律を保つのが難しくなる
- Cの「サイレントなセグフォルト・メモリ破損」に比べれば明確な改善だが、**Rustと違って、ルールを守る責任は依然としてプログラマ自身にある**

### 実際に踏んだバグの具体例(著者が実際に遭遇したものと、Rustでの対比)

| バグの種類 | Zigでの状況 | Rustでは |
|---|---|---|
| **`deinit`忘れによるメモリリーク** | `iter.deinit()`を呼び忘れる。テストアロケータが`MemoryLeakDetected`で検出 | `Drop`がスコープ終了時に自動実行されるため、**このバグ自体が存在しない**(所有権の仕組みそのもの) |
| **エラーパスでの`deinit`スキップ** | 2回目の`append`が失敗すると、初回分の`iter`が誰にも解放されず残る | `?`演算子による早期リターンでも`Drop`は必ず発火するため、**構造的に排除される** |
| **二重解放(double-free)** | 呼び出し階層をまたいで所有権の受け渡しを誤り、同じメモリを2箇所で`deinit`してしまう | `cache.push(result)`は`result`の所有権を**移動(move)**するため、その後誤って`drop(result)`を呼ぶこと自体が**コンパイルできない** |
| **構造体への格納失敗時の孤立確保(orphaned allocation)** | 文字列を複製(dupe)した直後、それを配列に追加する処理が失敗すると、複製した分だけ迷子のメモリになる | `Vec::push`は値を移動して成功するか、OOM(メモリ不足)で異常終了するかのどちらかで、**「確保はしたが繋がっていない」中間状態を作りようがない** |

著者は各バグについて「Zigの`TestAllocator`(失敗を意図的に注入するテスト用アロケータ)が実際にこれらを検出してくれる」と評価しつつも、「**Rustではこの種のバグのクラスが、そもそも設計上存在しえない**」という違いを繰り返し強調している。前回・前々回の記事で解説した「所有権:所有者がスコープを抜けると自動的に破棄される」「借用:可変の参照は同時に1つまで」というRustの仕組みが、まさにこれらのバグを構造的に防いでいることが、この記事でも裏付けられている形。

## 6. エコシステムの若さ

Zigのエコシステムはまだ非常に若い。

- ライブラリの絶対数が少ない
- 正規表現ライブラリ(`mvzr`)ですら、Unicodeプロパティエスケープ(`\p{...}`)未対応など、基本機能に穴がある
- 標準ライブラリ自体のAPIがバージョンごとに変わる

著者はこれらを「想定内」としつつも、記録に残す価値があるとしている。

## 総合評価(著者の結論)

> 「言語としてはRustとは全く違うが(当然だが)、**総じて非常に良い印象を持った**。シンプルで、モダンで、爆速。Cの真の後継となる可能性を感じる。一方で、まだ若い言語であることも事実で、言語の形自体がところどころ未完成に感じられる。成熟するにつれて、より快適な機能や糖衣構文が増えていくだろう」

著者は今後もZigエコシステムへの貢献を続けたいとしつつ、記事の最後に「**文体・エラーハンドリングの整形にAIの助けを借りた**」という開示も付記している。

## まとめ:この記事から読み取れる、Zig vs Rustの本質的な違い

| 観点 | Rust | Zig |
|---|---|---|
| メモリ安全性の保証 | 所有権システムがコンパイル時に強制 | プログラマが規律(init/deinit)を守ることに依存、TestAllocatorで検出支援 |
| コードの見た目 | 関数型寄り(コンビネータ・不変データ) | 手続き型寄り(ループ・ミューテーション) |
| 学習・開発体験 | IDEサポートが充実 | CLI中心、IDEサポートは発展途上 |
| プロジェクト構造 | 深い階層になりがち | フラットな構造を自然に維持しやすい |
| エコシステムの成熟度 | 高い(7年以上の実務経験に耐える) | 若い(基本ライブラリにも機能不足あり) |

「所有権・借用・データ競合防止」というRustの強みが、**Zigとの直接比較を通じて、より具体的に裏付けられた**内容の記事だった。Zig自体は「Cの正当な後継候補」として好意的に評価されており、低レベル言語の選択肢として今後も注目に値する。

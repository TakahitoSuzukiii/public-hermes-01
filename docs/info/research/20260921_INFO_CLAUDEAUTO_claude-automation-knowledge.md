## 1. ITインフラ/サーバ運用保守のルーティンワーク自動化（Excel集計・週次レポート）

### 本当に週3時間削減できるのか？Claude CodeでExcel集計・週次レポート自動化を検証してみた
- 出典: https://zenn.dev/makolab/articles/d16e46ea39edaa
- 内容: 「Claude Codeで週3時間・年間150時間削減できる」という元記事の主張を、筆者が東京・大阪・名古屋3支店の架空売上データを使って実際に再現検証した記事です。①1支店の月次集計→②3支店分のExcelファイル統合→③グラフ付き週次レポート生成、という3段階を日本語の指示文だけで実行し、322件のレコード統合やグラフ埋め込みまで一度もエラーなく完了したと報告しています。
- 便利さ: 「本当にその効果は出るのか」を疑い、実際に手を動かして検証するという姿勢自体が参考になります。かかった時間（準備込みで1時間弱）や手作業との比較（体感30分〜1時間）を具体的に示しており、導入効果を社内に説明する際の材料として使いやすい記事です。
- 注意点: pandas・matplotlib等のライブラリ導入は初回のみ必要で、グラフに日本語ラベルを入れる場合はフォント指定を明示しないと文字化けする点に要注意（この記事では対策済みですが、初めて試す場合は完成後の目視確認を推奨しています）。

## 2. ゼロデイ攻撃対策・セキュリティ運用の自動化

### 【第5回・番外編】ゼロから作る脆弱性管理台帳 - Claude Codeで半自動化してみた
- 出典: https://note.com/tetsato/n/n7909fa6d9c76
- 内容: 個人エンジニアが、CVE（共通脆弱性識別子）・KEV（実際に悪用が確認された既知の脆弱性）調査を専用スクリプト（`run_vuln_check.py`）とClaude Codeを組み合わせて半自動化した事例。CPE解決やNVD API通信などの機械的処理はすべてスクリプト側に担当させ、Claude Codeの役割は「自然言語の依頼を期間指定に変換する」「候補の製品レベル最終判断（人間に確認が必要なら聞く）」の2点に限定する設計です。
- 便利さ: CLAUDE.md（Claude Codeへの作業手順ファイル）の全文を公開しており、「AIに自由に調査させず、決められたスクリプトを必ず実行させる」「判断がつかない候補は憶測で倒さず人間に確認する」というガードレールの書き方が具体的で、そのまま自分の運用に応用しやすい内容です。
- 注意点: Microsoft製品の脆弱性情報（MSRC）はページが自動取得できない仕組みのため、その部分だけは人間がCSVをダウンロードして渡す必要があり、完全自動化ではなく「機械的処理はスクリプト、判断はAI、一部データ取得は人間」という3者分業になっている点は導入前に理解しておく必要があります。

## 3. インフラ/クラウドエンジニア・SRE・CI/CD・Playwrightによる自動化

### Claude × Devinで実現するAI駆動開発ワークフロー
- 出典: https://techblog.zozo.com/entry/ai-driven-dev-with-claude-and-devin
- 内容: ZOZOの新規事業部が、Claude（レビュー・分類判定・自動承認の判断）とDevin（実装・CIエラー修正）を役割分担させたAI駆動開発ワークフローの事例。GitHub Actionsワークフローが「CI失敗時の自動修正」「レビュー指摘の自動修正」「AIコンテキストの週次更新」を自動で呼び出す一方、認証・認可の変更やシークレット関連など重要な変更は`!human_review`コマンドで必ず人間承認に回す設計です。
- 便利さ: 同期的に結果を返すClaude（判断向き）と、非同期で一貫作業ができるDevin（実装向き）を「実行方式の違い」で明確に役割分担している点が、複数のAIサービスを併用する際の設計指針として参考になります。人間レビューが必要なケースを列挙している点もそのまま流用しやすい実務知見です。
- 注意点: この仕組みはGitHub Actions・Slack・Devin APIなど複数サービスの連携基盤を前提としており、小規模チームがいきなり全体を再現するにはやや構成が大きく、まずは「CI失敗時の自動修正」など1機能から段階導入する方が現実的です。

### Claude Code と Playwright MCP を用いたE2Eテスト自動化スキルの構築
- 出典: https://recruit.group.gmo/engineer/jisedai/blog/claude-code-playwright-e2e-test-automation/
- 内容: GMOインターネットグループ グループ研究開発本部が、従来型のE2E（End-to-End）テスト（コードでPage Object・セレクタを書く方式）とは別に、Playwright MCPを使い「テストコードを書かず、自然言語のMarkdown計画で動作確認する」スキルを構築した事例。「ログイン手順など変わらない知識（references）」「issueごとに毎回生成する計画（plans）」「実行結果の証跡（reports）」の3層に情報を分離し、人間が確認するのは計画承認の1ゲートのみに絞っています。
- 便利さ: 「繰り返し回す回帰スイートは従来型のコードテスト、個別修正の事後確認は自然言語エージェント」という使い分けの整理が明快で、E2Eテストの資産がまだない小規模プロダクトが「まず何から自動化すべきか」を考える際の判断軸として役立ちます。
- 注意点: 自然言語エージェント方式は探索的に動くため実行が遅くトークン消費も大きく、決定的に高速再生できる従来型コードテストと比べて「繰り返し同じ確認を高速に回す」用途には向かない、という位置づけの違いを理解した上で使い分ける必要があります。

## 4. GitHubのawesomeシリーズ（awesome-claude-code等）

### awesome-claude-code-toolkit
- 出典: https://github.com/rohitg00/awesome-claude-code-toolkit
- 内容: 135種のエージェント、35種の厳選スキル、42種のコマンド、176以上のプラグイン、20種のフック、15のルール、7つのテンプレート、14のMCP設定など、Claude Code関連リソースを網羅した大型キュレーションリポジトリです。star数2,630・fork数965（2026年9月確認時点）、Apache License 2.0（改変・商用利用ともに認められるオープンソースライセンス）が明記されており、2026年5月時点でも更新が続いています。
- 便利さ: 単一カテゴリに偏らず「エージェント」「スキル」「コマンド」「MCP設定」まで横断的に整理されているため、これから自分のワークフローに合う部品を探す際の一次候補リストとして使いやすい規模感です。
- 注意点: 本家awesome-claude-code（star数5万超）と比べるとコミュニティ規模はまだ小さく、個々のエージェント・スキルの中身（外部通信の有無、権限範囲など）は導入前に必ず目視確認してください。AGENTS.mdの外部スキル導入時信頼性チェック（Star数・作者情報・メンテナンス状況・ライセンス・コード内容）に沿った精査が必要です。

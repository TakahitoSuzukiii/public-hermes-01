# 所有権(Ownership)・借用(Borrowing)・ライフタイム(Lifetime):Rust最大の壁を理解する

- **記録日:** 2026-09-15
- **位置づけ:** `docs/hermes/016`(Rust入門記事)の続編。Rust学習で最初につまずきやすい3つの独自概念(所有権・借用・ライフタイム)を、それぞれ詳しく整理した解説記事。

## 1. 所有権(Ownership) — 「誰が責任を持ってメモリを片付けるか」

### 基本ルール

Rustのメモリ管理は、たった3つのルールに支えられている。

1. **すべての値には、所有者(owner)と呼ばれる変数がただ1つ存在する**
2. **所有者は同時に1つしか存在できない**
3. **所有者がスコープ(コードブロック)を抜けると、その値は自動的に破棄される**

```rust
{
    let s = String::from("hello"); // sがこの値の所有者になる
    // sを使った処理
} // このスコープが終わると、sは自動的に破棄され、メモリが解放される
```

GC(ガベージコレクタ)のように「使われなくなった頃合いを見て」片付けるのではなく、**「どこでスコープが終わるか」という、コンパイル時に確定する情報だけを使って、片付けるタイミングを決定論的に決める**のがポイント。だから実行時のオーバーヘッドがほぼゼロになる。

### 「ムーブ(move)」という独特の挙動

Rustで最初に驚かれるのが、この挙動である。

```rust
let s1 = String::from("hello");
let s2 = s1; // ここで所有権が s1 から s2 に「移動(ムーブ)」する

println!("{}", s1); // ← コンパイルエラー！s1はもう使えない
```

他の言語では「s2にs1をコピーしただけ」と考えがちだが、Rustでは**「所有者は1つしか存在できない」というルールを守るため、代入した瞬間に所有権がs1からs2へ移動し、s1は無効になる**。これにより、「同じメモリ領域を2つの変数が同時に指していて、片方が解放した後にもう片方が誤ってアクセスしてしまう」という、C/C++で頻発するバグ(dangling pointer、解放済み領域へのアクセス)が、**コンパイルの時点で機械的に防がれる**。

### なぜこんな面倒な仕組みが必要なのか

「1つの値に対して、責任者(所有者)は常に1人だけ」というルールを徹底することで、**「誰かが解放したメモリに、別の誰かがまだアクセスしようとする」という事故そのものを、実行前の段階で構造的に起こりえなくしている**、というのが所有権の本質である。

## 2. 借用(Borrowing) — 「所有権を渡さずに、一時的に使わせてもらう」

所有権のルールだけだと、「関数に値を渡すたびに所有権が移動してしまい、呼び出し元がその値を使えなくなる」という、非常に不便な状況になる。これを解決するのが「借用」である。

### 参照(reference)という仕組み

```rust
fn calculate_length(s: &String) -> usize { // &をつけて「借用」する
    s.len()
} // ここでsはスコープを抜けるが、借用しているだけなので何も破棄されない

let s1 = String::from("hello");
let len = calculate_length(&s1); // &s1で「参照」を渡す(所有権は渡さない)

println!("{}の長さは{}", s1, len); // s1はまだ使える！
```

`&`をつけることで、**「所有権は渡さず、一時的に値を覗き見・利用させてもらう」**という借用が成立する。関数を抜けても元の所有者(`s1`)には影響がなく、呼び出し元は引き続きその値を使える。

### 借用には厳格なルールがある(データ競合の防止)

借用には、コンパイラが機械的にチェックする2つの重要なルールがある。

1. **「不変の参照(読み取り専用の借用)」は同時にいくつでも作れる**
2. **「可変の参照(書き込み可能な借用)」は、同時に1つしか作れない。しかも可変の参照がある間は、不変の参照も一切作れない**

```rust
let mut s = String::from("hello");

let r1 = &s;     // OK:不変の借用
let r2 = &s;     // OK:不変の借用は複数OK
// let r3 = &mut s; // ← ここでr1・r2が生きている間はエラー！
```

このルールが守っているのは、**「誰かがデータを読んでいる最中に、別の誰かがこっそり書き換えてしまう」というデータ競合(data race)**である。特にマルチスレッドプログラミングでは、この種のバグは**実行するたびに症状が変わる、極めて発見・再現が困難なバグ**として悪名高いが、Rustではこのルールにより**コンパイルが通った時点で、データ競合が原理的に起こりえないことが保証**される。これがRustが「怖くない並行処理(fearless concurrency)」と呼ばれる所以である。

### 「借用チェッカー(borrow checker)」というコンパイラの門番

これら所有権・借用のルールを実際にチェックしているのが、Rustコンパイラに内蔵された**「借用チェッカー」**という仕組みである。ルール違反があれば、実行前の段階で必ずコンパイルエラーとして弾かれる。**「動いてから初めてバグに気づく」のではなく、「そもそも危険なコードは動かせない」**という設計思想が徹底されている。

## 3. ライフタイム(Lifetime) — 「参照が有効な期間を、型として明示する」

### なぜライフタイムが必要になるのか

借用(参照)を使っていると、次のような**「元のデータが先に消えてしまい、参照だけが取り残される」**という危険な状況が起こり得る。

```rust
let r;                // rを宣言(まだ値なし)
{
    let x = 5;
    r = &x;           // xへの参照をrに代入
}                     // ← ここでxはスコープを抜けて破棄される
println!("{}", r);    // ← rはもう存在しないxを指している(ダングリング参照)
```

これは「参照先が既に消えているのに、その参照を使おうとする」という典型的な事故パターンである。**ライフタイムは、この事故を防ぐために「この参照は、いつまで有効なのか」をコンパイラに伝える仕組み**である(上記の例は実際にはコンパイルエラーになり、そもそも実行されない)。

### ライフタイム注釈の書き方

複数の参照を扱う関数では、「どの参照とどの参照が、同じ期間だけ有効なのか」をコンパイラに明示する必要が出てくる。

```rust
fn longer<'a>(s1: &'a str, s2: &'a str) -> &'a str {
    if s1.len() > s2.len() { s1 } else { s2 }
}
```

`'a`という記法(アポストロフィ+名前)が「ライフタイム注釈」である。この例では「**引数`s1`と`s2`、そして戻り値の参照は、すべて同じ期間だけ有効である**」ということをコンパイラに伝えている。これにより、コンパイラは「戻り値の参照が、元のデータより長生きしてしまう(=ダングリング参照になる)」ような呼び出し方を、事前に検出して弾けるようになる。

### 「ライフタイムを書く」のは、新しいルールを作っているわけではない

初心者が誤解しやすいポイントだが、**ライフタイム注釈は「参照の有効期間を新たに決めている」わけではない。** 実際の有効期間は、あくまでコードの構造(スコープ)によって既に決まっている。ライフタイム注釈は、**「複数の参照の間に、どういう関係性があるか」をコンパイラに教えてあげるための、いわば"注釈"**に過ぎない。多くの単純なケースでは、コンパイラが自動的にライフタイムを推論してくれる(「ライフタイム省略規則」)ため、実際に手で書く場面は思ったより多くない。

## まとめ:3つの概念のつながり

| 概念 | 何を防ぐか | 一言で言うと |
|---|---|---|
| **所有権** | 二重解放、解放済みメモリへのアクセス | 値の責任者は常に1人だけ |
| **借用** | データ競合(同時読み書きの衝突) | 所有権を渡さず一時的に貸し借りする、貸し借りのルールを厳格化 |
| **ライフタイム** | ダングリング参照(消えたデータへの参照) | 「この参照はいつまで有効か」を型で明示する |

3つとも共通しているのは、**「実行時に初めて発覚するバグを、コンパイル時に機械的に検出できるようにする」**という設計思想である。学習の初期段階では「コンパイラにやたら怒られる言語」という印象を持ちやすいが、これは裏を返せば**「コンパイルさえ通れば、この種の深刻なバグはほぼ起こらない」という強力な保証**を得ていることを意味する。この「最初は厳しいが、後になるほど安心感が大きい」という体験こそが、多くの開発者がRustを高く評価する最大の理由である。

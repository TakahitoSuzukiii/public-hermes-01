# Rustのデータ競合を、他言語の具体例と用語比較で理解する

- **記録日:** 2026-09-15
- **位置づけ:** `docs/hermes/018`(借用ルールとデータ競合防止の解説)の発展編。Java・C++・Goそれぞれで実際にデータ競合がどう発生するかを具体的なユースケースとともに解説し、「データ競合」「レースコンディション」「コリジョン」「コンフリクト」という混同されやすい用語の違いを整理する。Rust4部作の最終編。

## Java:HashMapの非同期アクセスで起きる「サイレントなデータ破壊」

### 具体的な発生シーン

```java
Map<String, Integer> map = new HashMap<>(); // スレッドセーフでない普通のHashMap

// スレッドAとスレッドBが同時に実行
Runnable task = () -> {
    for (int i = 0; i < 1000; i++) {
        map.put("key" + i, i);
    }
};
new Thread(task).start();
new Thread(task).start();
```

### 何が起きるか

`HashMap`は内部で、格納するデータ量が増えると**「リサイズ(再構築)」**という処理を行う。このリサイズの最中に、**別のスレッドが同時に書き込もうとすると**、以下のような深刻な問題が起こり得る。

- 一方のスレッドが古いテーブル(リサイズ前)にまだ書き込んでいる間に、もう一方が新しいテーブル(リサイズ後)を使い始め、**書き込んだデータが消失する**
- 最悪のケースでは、内部の連結リスト構造が壊れて**無限ループに陥り、CPU使用率が100%に張り付いたまま応答しなくなる**(実際にJavaの初期バージョンで大きな問題になった既知の不具合パターン)

### Javaでの対処法

`java.util.concurrent.ConcurrentHashMap`という、**マルチスレッドでの利用を前提に内部で細かくロック(セグメント単位のロック等)を管理している専用クラス**を使うのが定石。「普通のHashMapを使うか、ConcurrentHashMapを使うか」を**プログラマ自身が判断して選ばなければならず、間違った方を選んでもコンパイルは通ってしまう**、というのがJavaの弱点。

## C++:`shared_ptr`の参照カウントで起きる「静かな二重解放」

### 具体的な発生シーン

```cpp
std::shared_ptr<int> ptr = std::make_shared<int>(42);

// スレッドAとスレッドBが、同じptr変数自体に対して
// 「非const関数(代入・reset等)」を同時に呼び出す
std::thread t1([&ptr]() { ptr = std::make_shared<int>(1); }); // 書き込み
std::thread t2([&ptr]() { ptr.reset(); });                    // 書き込み
```

### 何が起きるか

`shared_ptr`は「何人がこのデータを参照しているか」を数える**参照カウンタ**の増減自体は、内部的にアトミック(不可分)な操作として安全に設計されている。**しかし、`shared_ptr`という変数「箱」自体を、複数スレッドから同時に書き換える(代入・reset等)ことは全く保護されておらず、公式リファレンス(cppreference)でも明確に「データ競合が発生する」と警告**されている。結果として、**同じメモリ領域が二重に解放されてしまう(double-free)**という、C++で最も悪名高いクラッシュ・脆弱性の原因になり得る。

### なぜ危険なのか

C++の規格上、**データ競合が起きた時点でプログラムの挙動は「未定義動作(undefined behavior)」**と定義されている。これは「たまたま今回はクラッシュしなかった」としても、**コンパイラの最適化次第でいつ何が起きても仕様上は問題ない、という極めて危険な状態**を意味する(後述の用語解説で詳しく触れる)。

### C++での対処法

`std::atomic<std::shared_ptr<T>>`(C++20以降)や、`std::mutex`による明示的な排他制御が必要。

## Go:マップへの並行書き込みで即座にクラッシュする(意図的な設計)

### 具体的な発生シーン

```go
m := make(map[string]string)

go func() {
    m["1"] = "a" // ゴルーチン1の書き込み
}()
go func() {
    m["2"] = "b" // ゴルーチン2の書き込み(同時に発生)
}()
```

### 何が起きるか

Goのマップは、**複数のゴルーチン(Goの軽量スレッド)から同時に書き込まれることを、実行時に検出すると即座にプログラムをクラッシュさせる**という設計になっている。これはJava/C++と対照的な「潔さ」。**「気づかれないまま壊れたデータで処理が続く」よりは、「その場で派手に落として、バグの存在を強制的に知らせる」方が安全、という設計思想**が反映されている。

### 検出ツール

Go言語は**`-race`という組み込みのデータ競合検出ツール**を標準搭載している。

```bash
go run -race main.go
```

これを使うと、実際に問題が発生していなくても(タイミング次第で発生しなかった場合でも)、**「危険な並行アクセスのパターンが存在すること」自体を検出**してくれる。

### Goでの対処法

`sync.Mutex`によるロック、または`sync.Map`(並行アクセス前提のマップ実装)を使う。

## 3言語の対処法の違い、まとめ

| 言語 | 何も対策しないとどうなるか | 検出のタイミング |
|---|---|---|
| **Java** | サイレントにデータが壊れる、最悪は無限ループ | 実行時、しかも稀にしか発生せず気づきにくい |
| **C++** | 未定義動作(何が起きても仕様上OKとされる、最悪クラッシュ・脆弱性) | 実行時(発生確率は環境依存で再現困難) |
| **Go** | 実行時に即座にクラッシュ(`-race`使用時) | 実行時(`-race`ツール使用時のみ確実に検出) |
| **Rust** | **そもそもコンパイルが通らない** | **コンパイル時(実行前)** |

Rustだけが「実行してみないと分からない」という段階を経ずに、**書いた瞬間・ビルドした瞬間に弾かれる**という点が、他の3言語との決定的な違いである。

## 用語の違い:データ競合・レースコンディション・コリジョン・コンフリクト

似たような文脈で使われがちなこれらの用語だが、**指している対象が全く異なる**。

### 1. データ競合(Data Race) vs レースコンディション(Race Condition)

この2つは**しばしば混同されるが、実は別の概念**である。

| | データ競合 | レースコンディション |
|---|---|---|
| **定義** | 複数スレッドが**同じメモリ位置**に同時アクセスし、**少なくとも1つが書き込み**で、**同期の仕組みがない**状態 | 処理の**実行タイミング・順序**によって、結果(意味・ロジック)が変わってしまう**設計上のバグ** |
| **範囲** | メモリレベルの、より技術的・限定的な現象 | より広い概念。データ競合を伴わなくても発生しうる |
| **C++での扱い** | 発生した時点で**未定義動作**(プログラム自体が仕様違反) | プログラムとしては合法だが、**結果が意図と異なる**(ロジックのバグ) |

**「全てのデータ競合はレースコンディションの一種だが、全てのレースコンディションがデータ競合とは限らない」**という関係である。例えば、`Mutex`できちんとロックを取っていて**データ競合は起きていない**のに、「ロックの取り方の順序が悪くて、意図しない処理順になってしまう」というケースは、**データ競合ではないがレースコンディションではある**、という状態になり得る。

### 2. コリジョン(Collision、衝突)

データ競合とは**全く別の文脈**で使われる言葉。最も一般的なのは**「ハッシュ衝突(hash collision)」**で、これは**「異なる複数のデータが、たまたま同じハッシュ値・同じ格納場所に計算されてしまう」**という現象を指す。

- 例:Javaの`HashMap`で、キー`"apple"`と`"grape"`が偶然同じ内部インデックスに割り当てられる、といった状況
- これは**並行処理(マルチスレッド)とは無関係に、単一スレッドでも起こりうる**、純粋にデータ構造上の性質である
- ただし冒頭のJavaの例のように、**「ハッシュ衝突の解決処理」と「データ競合」が組み合わさって、より深刻な問題を引き起こす**こともある(1つのバケツ内で複数キーが衝突している状態で、さらに複数スレッドが同時に書き込むと、片方の変更が消えるといった具合)

### 3. コンフリクト(Conflict、競合・対立)

こちらも文脈によって意味が変わる、より広い言葉。プログラミングの世界で最もよく聞くのは**「マージコンフリクト(merge conflict)」**で、これは**「Git等のバージョン管理で、2つのブランチが同じ箇所を異なる内容に変更していて、自動的に統合できない」**という状態を指す。

- これは**人間(開発者)同士が、同じコードの同じ箇所を別々に編集した**という、**開発プロセス上の衝突**であり、プログラムの実行時の話ではない
- データ競合とは**発生するレイヤーが全く違う**(片や「実行時のメモリアクセス」、片や「ソースコード管理上の変更履歴」)ため、混同しないよう注意が必要

### まとめ表

| 用語 | 発生するレイヤー | 一言でいうと |
|---|---|---|
| **データ競合(Data Race)** | 実行時・メモリアクセス | 複数スレッドが無防備に同じメモリへ同時アクセス(うち1つは書き込み) |
| **レースコンディション(Race Condition)** | 実行時・ロジック | タイミング次第で結果が変わってしまう設計バグ(データ競合より広い概念) |
| **コリジョン(Collision)** | データ構造 | 異なるデータが同じハッシュ値・格納位置に偶然一致する現象 |
| **コンフリクト(Conflict)** | 開発プロセス(バージョン管理) | 複数人の変更が同じ箇所で衝突し、自動統合できない状態 |

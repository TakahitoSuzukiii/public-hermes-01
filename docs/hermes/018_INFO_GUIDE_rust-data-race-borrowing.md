# 借用ルールがマルチスレッドのデータ競合をどう防ぐか — 実例で理解する「怖くない並行処理」

- **記録日:** 2026-09-15
- **位置づけ:** `docs/hermes/017`(所有権・借用・ライフタイム解説)の発展編。「借用のルールが、なぜマルチスレッドプログラミングのデータ競合を防げるのか」を、実際のコード例(コンパイルエラーになる例・正しく直した例)を交えて詳しく解説する。Rust3部作の最終編。

## そもそも「データ競合」とは何か

**データ競合(data race)** とは、**複数のスレッド(処理の流れ)が、同じデータに同時にアクセスし、そのうち少なくとも1つが「書き込み」であるときに発生する、予測不能な不整合**のことです。

身近な例で考えると分かりやすいです。

> 銀行口座の残高「100円」を、2つの窓口が同時に処理しようとしている。
> - 窓口A:残高を読み取り(100円) → +50円して書き込む
> - 窓口B:同時に残高を読み取り(100円) → +30円して書き込む
>
> 本来は「100+50+30=180円」になるべきなのに、**タイミング次第では片方の更新が消えてしまい、150円や130円で確定してしまう**ことがある。

これがデータ競合です。厄介なのは、**発生するかどうかが「実行するタイミング」に依存する**ため、テストで再現しにくく、本番環境でだけ稀に発生する、極めて発見困難なバグになりやすい点です。

## Rustの借用ルール(おさらい)

前回記事で解説した通り、Rustの借用には以下のルールがあります。

1. **不変の参照(読み取り専用)は、同時にいくつでも作れる**
2. **可変の参照(書き込み可能)は、同時に1つしか作れない。可変の参照がある間は、不変の参照も一切作れない**

このルールは、**単一スレッド内であっても厳格に適用**されます。しかし、このルールの真価が最も発揮されるのが、**複数スレッドにまたがってデータを共有する場面**です。

## 実例①:そのままではコンパイルが通らない(意図的な失敗例)

まず、他の言語であれば普通に書けてしまう「危険なコード」を、Rustで書こうとするとどうなるかを見てみます。

```rust
use std::thread;

fn main() {
    let mut counter = 0;

    let handle1 = thread::spawn(|| {
        counter += 1; // ← スレッド1がcounterを書き換えようとする
    });

    let handle2 = thread::spawn(|| {
        counter += 1; // ← スレッド2も同時にcounterを書き換えようとする
    });

    handle1.join().unwrap();
    handle2.join().unwrap();

    println!("{}", counter);
}
```

このコードは**コンパイルの時点でエラーになります。** 大まかに言うと、以下のような趣旨のエラーメッセージが出ます。

```
error[E0373]: closure may outlive the current function, but it borrows `counter`, which is owned by the current function
error: cannot borrow `counter` as mutable, because it is not declared as mutable... (複数スレッドから可変の参照を同時に持とうとしている)
```

**「複数のスレッド(=複数の実行の流れ)が、同じ`counter`という変数を、同時に書き込み可能な状態で参照しようとしている」**という、まさにデータ競合そのものの構造を、Rustのコンパイラは**実行する前の段階で検出して弾いています。** これは前回解説した「可変の参照は同時に1つまで」という借用ルールが、スレッドをまたいでも例外なく適用されているためです。

## なぜコンパイラはスレッドをまたいだ危険性まで検出できるのか:`Send`と`Sync`

Rustには、型が「スレッド間でどう安全にやり取りできるか」を表す、2つの特別なマーカー(目印)があります。

| マーカー | 意味 |
|---|---|
| **`Send`** | その型の値を**別のスレッドに所有権ごと渡しても安全**であることを示す |
| **`Sync`** | その型への**参照を、複数のスレッドから同時に共有しても安全**であることを示す |

普通の変数(上記の`counter`のような単純な整数)は、**複数スレッドから同時に書き込み参照を共有すること自体が想定されていない**ため、コンパイラはこの「安全にスレッド間共有できるか」の要件を満たさないコードを、コンパイルエラーとして機械的に拒否します。**「気をつけて書く」のではなく、「そもそも危険な書き方自体が言語レベルでできない」**、という所有権・借用ルールの延長線上に、マルチスレッド安全性が組み込まれているのがポイントです。

## 実例②:正しく直したコード(`Arc` + `Mutex`)

では、複数スレッドで安全にデータを共有・更新するには、どう書けばよいのでしょうか。Rustでは、以下の2つの道具を組み合わせるのが定番です。

| 道具 | 役割 |
|---|---|
| **`Arc`(Atomic Reference Counted)** | 複数のスレッドで、**同じデータの所有権を安全に共有**するための仕組み(参照カウント方式) |
| **`Mutex`(Mutual Exclusion、相互排他)** | データへの**アクセスを1スレッドずつ順番に制限する「鍵」**の仕組み |

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0)); // Arcで共有可能に、Mutexで排他制御
    let mut handles = vec![];

    for _ in 0..2 {
        let counter = Arc::clone(&counter); // 参照カウントを+1して、各スレッドに渡す
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap(); // ロックを取得(他のスレッドは待たされる)
            *num += 1;
            // ここでロックが自動的に解放される(スコープを抜けるタイミングで)
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("結果: {}", *counter.lock().unwrap()); // → 2 (必ず正しい値になる)
}
```

### このコードで何が起きているか

1. **`Arc::new(Mutex::new(0))`** — 「複数スレッドで共有できる形(Arc)」で包んだ上に、さらに「同時に1スレッドしかアクセスできない鍵(Mutex)」をかけている
2. **`Arc::clone(&counter)`** — 実際のデータをコピーするのではなく、**「同じデータへの共有権」を、参照カウントを増やしながら複製**している(参照カウントが0になった時点で、実際のメモリが解放される)
3. **`counter.lock().unwrap()`** — ロック(鍵)を取得しようとする。**既に別のスレッドがロックを保持していれば、そのスレッドはロックが解放されるまで待たされる**。これにより、「同時に2つのスレッドが同時に書き込む」という状況が構造的に発生しなくなる
4. ロックの取得によって得られる`num`は、その瞬間**「今このスレッドだけが持つ、唯一の可変の参照」**であることが保証される。これは前回解説した「可変の参照は同時に1つまで」という借用ルールと、完全に同じ構造です

**つまり`Mutex`は、「借用ルールの"可変の参照は1つまで"という制約を、実行時に(スレッドをまたいで)強制的に成立させるための仕組み」**だと理解すると、所有権・借用の話と自然につながります。

## まとめ:借用ルールとマルチスレッド安全性の関係

| 単一スレッドでの借用ルール | マルチスレッドでの対応 |
|---|---|
| 可変の参照は同時に1つまで | `Mutex`のロックで「今この瞬間、書き込めるのは1スレッドだけ」を実行時に保証 |
| 所有者は1つだけ | `Arc`で「複数スレッドが安全に所有権を共有できる」形に拡張(参照カウント方式) |
| コンパイル時にルール違反を検出 | `Send`/`Sync`により、スレッドをまたぐ危険な共有もコンパイル時に検出 |

Rustの借用チェッカーは、**単一スレッド内のメモリ安全性を守るために設計されたルールが、そのままマルチスレッドのデータ競合防止にも応用できる**、という設計上の一貫性を持っています。これが「Fearless Concurrency(怖くない並行処理)」と呼ばれる理由であり、**「コンパイルさえ通れば、データ競合は原理的に起こりえない」**という、他の多くの言語にはない強力な保証を実現しています。

### 補足:借用チェッカーが防げないこと

念のため補足すると、借用チェッカーが防ぐのは「**データ競合**」であり、以下のような**「ロジック上の問題」までは防げません**。

- **デッドロック**:複数の`Mutex`を使う際、スレッドAが「ロック1→ロック2」の順で、スレッドBが「ロック2→ロック1」の順でロックを取ろうとすると、お互いが相手の解放を待ち続けて永遠に止まってしまう状態。コンパイラはこの種の「循環待ち」を静的には検出できません
- **意図しない処理順序**:データ競合は防げても、「どちらのスレッドが先に実行されるか」という順序の保証まではしてくれません

これらはRustであっても、設計段階での注意が引き続き必要な領域です。

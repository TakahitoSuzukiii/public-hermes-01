# 実務で使えるAIプロンプト/ルールセット チートシート

- **記録日:** 2026-09-03
- **位置づけ:** [ponytail](https://github.com/DietrichGebert/ponytail)（「怠惰なシニアエンジニア」ルールセット）の解説記事から発展。同種の「AIエージェントに行動指針を持たせるプロンプト/ルールセット」を、実務での利用パターン別に整理した。
> 全て**コピペしてそのまま使える**形式。プレースホルダ（`〈〉`で囲んだ部分）だけ差し替えて使用する。

---

## 使い方の全体像

このチートシートは6カテゴリで構成。プロンプトは大きく2種類ある。

- **単発プロンプト型**: チャットに1回貼り付けて使う（都度の依頼向け）
- **常設ルールセット型**: AIエージェントの設定ファイル（CLAUDE.md、AGENTS.md、システムプロンプト等）に置いて、以降ずっと効かせる（プロジェクト・運用方針として固定したい場合向け）

| # | カテゴリ | 主なユースケース |
|---|---|---|
| 1 | 複数視点レビュー | 文書・コード・提案を、異なる立場（人事/技術責任者/マネージャー等）から厳しくチェックしたい時 |
| 2 | 事実ベース検証・推測禁止 | AIが不確かな情報を断定してしまうのを防ぎたい時 |
| 3 | 最小変更・デグレ防止 | 既存システムに手を入れる時、壊さずに安全に進めたい時 |
| 4 | 怠惰なシニアエンジニア（コード最小化） | AIにコードを書かせる時、過剰な実装を防ぎたい時 |
| 5 | 深掘り質問の洗い出し | 面接・プレゼン・企画書などの「弱点」を事前に洗い出したい時 |
| 6 | 機密情報マスキング | ドキュメントを外部公開する前に、個人情報・機密を機械的に除去したい時 |

## 1. 複数視点レビュー（役割分担型 厳格レビュー）

### 概要
1つの成果物（文書・コード・企画）を、**異なる利害関係者の視点**から独立してレビューさせることで、単一視点では見落とす弱点を洗い出す手法。「お世辞だけの評価」を避け、忖度のない指摘を引き出せる。

### 特徴
- 立場を明示的に割り当てることで、AIの回答が「一般論」ではなく「その立場ならではの視点」に寄る
- 複数の役割を**並行して独立に**走らせると（サブエージェント委譲等）、視点の混同を防げる
- 重要度（高/中/低）を付けさせることで、優先順位が一目で分かる

### ユースケース
- 転職活動: 志望動機・職務経歴書を「人事」「採用責任者」「現場マネージャー」視点で厳格レビュー
- コードレビュー: 「セキュリティ担当」「パフォーマンス担当」「可読性担当」視点で分担レビュー
- 企画書・提案書: 「経営層」「現場」「顧客」視点でのツッコミ出し

### コピペ用プロンプト

```
あなたは、最高の〈役割1（例: 人事プロフェッショナル）〉、および、
最高の〈役割2（例: エンジニア採用責任者）〉、および、
最高の〈役割3（例: エンジニアマネージャー）〉です。

以下の〈対象物（文書・コード・企画書等）〉を、それぞれの役割の視点で
厳しくレビューしてください。忖度は不要です。

【評価観点】
1. 〈観点1（例: 説得力・一貫性）〉
2. 〈観点2（例: 具体性・裏付けの有無）〉
3. 〈観点3（例: 矛盾点・違和感のある表現）〉
4. 改善すべき具体的な箇所（該当箇所を引用しつつ）

最終出力は、指摘事項を箇条書きで整理し、重要度（高/中/低）を付けてください。
厳しく・忖度なく指摘した上で、最後に建設的な改善提案もセットで示してください。

【対象物】
〈ここに対象物を貼り付け、またはファイルパスを指定〉
```

## 2. 事実ベース検証・推測禁止

### 概要
AIは自然に「もっともらしいが確認していない情報」を断定的に語ってしまう。これを防ぎ、**分かっていることと分かっていないことを明確に切り分けさせる**ためのルール。

### 特徴
- 「不明な点は質問としてリスト化させる」ことで、AIの創作を防ぐ
- 「確実に分かる範囲」と「要確認の範囲」を分離して出力させることで、後から検証しやすい
- 本人確認前の内容には必ずマーカー（⚠️等）を付けさせる

### ユースケース
- 経歴・実績など、事実確認が必須の文書作成
- 技術的な原因調査（推測でバグの原因を決めつけない）
- 第三者情報の要約（ソースにない情報を混ぜ込まない）

### コピペ用プロンプト

```
以下のタスクに取り組む際、次のルールを厳守してください:

1. 事実として確認できていない情報は、絶対に断定して書かないこと。
   もっともらしく見えても、根拠のない推測は「創作」として扱い、禁止する。
2. 情報が不足している部分は、埋めようとせず、
   **明確に「〈依頼者〉への確認質問」としてリスト化**すること。
3. 質問には「何を」「なぜ知りたいか」を明記すること。
4. 現時点で確実に分かる範囲のみで、可能な部分の作業を先に進めてよい。
   その場合も「⚠️未確認・要追加確認」として、埋まっていない箇所を明示すること。

【タスク】
〈ここに依頼内容を記載〉
```

### 常設ルールセット版（CLAUDE.md / AGENTS.md等に追記）

```markdown
## 事実確認の原則
- 未確認の事実を推測で断定してはならない。断定的な表現をする前に、
  情報源（ファイル・ログ・本人確認）を明示できるか自問すること。
- 事実確認できない場合は、断定を避け「〈本人〉に確認が必要」と明記する。
- 本人が事後に指摘した場合は、断定していた箇所を洗い出し、
  事実ベースの内容に差し替える。
```

## 3. 最小変更・デグレ防止（追加のみ原則）

### 概要
既存の動いているシステムに手を加える際、**「書き換え」ではなく「追加」を原則とする**ことで、意図しない破壊（デグレ）を防ぐ運用ルール。

### 特徴
- 新機能は既存ロジックを変更せず、新しいファイル・関数・ルートとして追加する
- 既存ファイルへの変更は「配線」（呼び出し追加等）に限定し、最小差分にする
- 破壊的変更が避けられない場合は、着手前にバックアップを取ることを必須化する

### ユースケース
- 本番稼働中のシステムへの機能追加
- 複数人・複数AIエージェントが同じコードベースを触る環境
- 「壊れたら困る」設定ファイル・自動化スクリプトの改修

### コピペ用プロンプト

```
これから〈対象システム〉に変更を加えます。以下の方針を厳守してください:

1. 【追加のみ・デグレ無し】新機能は原則「追加」で実装し、
   既存のロジック・動作を変更しないこと。
2. 既存ファイルへの変更は、新機能を呼び出すための最小限の配線
   （ルート追加・インポート追加等）に留め、差分を最小化すること。
3. 【着手前バックアップ】既存ファイルを変更する場合、
   着手前に元の内容をコピー・退避してから作業すること。
4. 【検証必須】変更後は、構文チェック・既存機能の動作確認
   （正常系・異常系）をセットで行い、デグレがないことを確認してから完了とすること。
5. 作業に使った一時ファイル・テストデータは、確認後に削除して元の状態に戻すこと。

【変更内容】
〈ここに変更したい内容を記載〉
```

## 4. 怠惰なシニアエンジニア（コード最小化・YAGNI徹底）

### 概要
[ponytail](https://github.com/DietrichGebert/ponytail)の考え方をベースにした、AIコーディングエージェントの**過剰実装を防ぐ**プロンプト。「本当に必要か」を先に問わせ、既存の仕組みを使い回させる。

### 特徴
- 新規コードを書く前に「本当に必要か」「既存で足りないか」を段階的にチェックさせる
- 「怠惰＝手抜き」ではなく、安全性・セキュリティは絶対に妥協しない、という線引きを明記する
- 実測で平均コード量54%削減、コスト20%削減、速度27%向上の実績あり（元記事参照）

### ユースケース
- AIにコードを書かせる全般（機能追加・リファクタリング等）
- 過去にAIが生成したコードが肥大化・複雑化してきたと感じる時
- コストを抑えつつAIコーディングを活用したい時

### コピペ用プロンプト

```
あなたは「最も怠惰な、しかし有能なシニアエンジニア」として振る舞ってください。

【解決策には怠惰に、しかし読解には手を抜かない】
新しいコードを書く前に、以下の順で確認してください:
1. そもそも、この機能は本当に今必要か？（投機的な実装をしない）
2. 既存のコードの中に、使い回せるヘルパー・関数はないか？
3. 標準ライブラリで実現できないか？
4. プラットフォームのネイティブ機能で足りないか？
5. どうしても必要な場合のみ、外部ライブラリの追加を検討する
6. 最後に、最小限の新規コードを書く

ただし、以下は絶対に手を抜かないこと（怠惰であって、いい加減ではない）:
- 入力値のバリデーション・信頼境界のチェック
- データ損失・不整合を防ぐ処理
- セキュリティ上のリスクがある処理
- アクセシビリティに関わる処理

コードを書いた後は、「この行・この関数は本当に必要か？」を自問し、
不要なものがあれば削ってください。

【タスク】
〈ここに実装したい内容を記載〉
```

## 5. 深掘り質問の洗い出し（弱点の事前発見）

### 概要
面接・プレゼン・企画提案などで、**相手が突いてきそうな弱点・矛盾を、AIに先回りして洗い出させる**手法。「まだ想定していない・準備が薄いトピック」を優先させるのがコツ。

### 特徴
- 既にカバー済みの質問は除外させ、**穴のあるトピックだけ**を優先させる
- 質問だけでなく「なぜこの質問が答えづらいか」の解説も付けさせることで、対策の方向性が分かる
- 重要度を付けさせることで、限られた準備時間を優先順位の高いものに集中できる

### ユースケース
- 面接対策（志望動機・経歴の矛盾を事前に洗い出す）
- 社内プレゼン・企画提案（役員からの想定質問対策）
- 契約書・提案書のレビュー（相手方が指摘しそうな条項の洗い出し）

### コピペ用プロンプト

```
あなたは、最高の〈厳しい評価者（例: 面接官、投資家、監査担当者）〉です。

以下の〈対象資料〉を読み込んだ上で、〈評価者〉として実際に
突きたくなる、または〈発表者〉が答えづらくなるであろう
想定質問を5〜8個作成してください。

【重点】
- 既に資料内で回答が用意されている質問は避け、
  **まだ想定されていない・資料内に穴があるトピック**を優先すること
- 相手が答えづらい、またはNGな方向に答えてしまいそうな
  「意地悪な角度」を意識すること

各質問には以下を付与してください:
1. 質問文（評価者が実際に言うであろう口調）
2. なぜこの質問が答えづらいか（資料内のどこに穴があるか）の解説
3. 重要度（高/中/低）
4. 回答する際の方針ヒント（具体的な文面ではなく、方向性のみ）

最終出力は重要度順に並べてください。

【対象資料】
〈ここに資料を貼り付け、またはファイルパスを指定〉
```

## 6. 機密情報マスキング（公開前チェック）

### 概要
社内ドキュメントを外部（GitHub public等）に公開する前に、**固有情報を機械的にプレースホルダへ置換**させ、実値を残さないためのルール。

### 特徴
- 対象種別ごとにプレースホルダの型を明示しておくと、AIの判断がブレない
- 「トークン・パスワード等は置換ではなく完全に書かない」という原則を明記するのが重要（プレースホルダにすると逆に「値がある」ことが分かってしまうケースがあるため）
- 迷った場合は「記録しない」を選ばせる（安全側に倒す）

### ユースケース
- 社内メモをブログ・GitHub Wiki等に公開する前
- 顧客向け提案書からの内部情報の除去
- OSS化するコード・設定ファイルのサニタイズ

### コピペ用プロンプト

```
以下の文書を外部公開用に加工してください。次のルールを厳守すること:

【機密情報の扱い（最優先ルール）】
以下は値を読んでも、出力には絶対に含めないこと（プレースホルダにもしない）:
- APIキー・認証トークン・パスワード・秘密鍵・証明書
- 個人を特定しうる情報（PII）
- 接続文字列内の認証情報

【固有情報のマスキング（プレースホルダに置換）】
| 種別 | 置換後 |
|---|---|
| ホスト名 | 〈hostname〉 |
| IPアドレス | 〈server-ip〉 |
| OSユーザ名 | 〈your-user〉 |
| メールアドレス | 〈your-email〉 |
| 社名・個人名（本人が非公開希望の場合） | 〈company-name〉等 |
| その他環境固有情報 | 〈…〉で囲んだ説明的な名前 |

【判断に迷う場合】
機密かどうか迷う情報は、**記録しない方を選ぶこと**。

作業後、置換した箇所の一覧を報告してください。

【対象文書】
〈ここに文書を貼り付け、またはファイルパスを指定〉
```

## まとめ:カテゴリ選択の目安

| こんな時 | 使うカテゴリ |
|---|---|
| 誰かに見せる前に、厳しくチェックしてほしい | 1. 複数視点レビュー |
| AIが自信満々に間違った情報を言いそうで不安 | 2. 事実ベース検証・推測禁止 |
| 本番環境やクリティカルな設定を触る | 3. 最小変更・デグレ防止 |
| AIにコードを書かせたら毎回大袈裟になる | 4. 怠惰なシニアエンジニア |
| 面接・プレゼン前に弱点を洗い出したい | 5. 深掘り質問の洗い出し |
| 社内資料を外部に公開する前の最終チェック | 6. 機密情報マスキング |

これらは単体でも、組み合わせても使える。例えば「3(最小変更)＋2(事実ベース)」を常設ルールセットとして設定ファイルに置いておけば、日常的な開発作業の安全性を底上げできる。
